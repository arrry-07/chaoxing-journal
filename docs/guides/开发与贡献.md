# 开发与贡献

Android 业务入口是 [`study_assistant-1.1.0/local_app`](../../study_assistant-1.1.0/local_app)，当前版本以 [`pubspec.yaml`](../../study_assistant-1.1.0/local_app/pubspec.yaml) 为准。1.7.3+55 提高主/次版本并按正式 latest 规则发布；更早的 1.6.72+54 是非 latest 静默补丁。修改前阅读根目录 [AGENTS.md](../../AGENTS.md) 和相关实现、调用方及测试，保留已有修改。

## 环境与验证

使用 Flutter **3.44.9**（随附 Dart **3.12.2**）、JDK **17** 和 Android SDK **36**，与当前 [CI](../../.github/workflows/flutter-checks.yml) 保持一致。Android 构建配置还指定 NDK `28.2.13676358`。先用 `flutter --version`、`java -version`、`flutter doctor -v` 检查本机环境，再按需安装 Android 工具和接受 SDK 许可。

从仓库根目录执行：

```sh
cd study_assistant-1.1.0/local_app
flutter pub get --enforce-lockfile
flutter analyze --no-pub
flutter test --no-pub
flutter build apk --debug --no-pub --target-platform android-arm64,android-x64
```

这些检查与 CI 同源，依赖版本由已提交的 `pubspec.lock` 固定。不要为解决环境问题随意删除锁文件。构建结果通常为 `build/app/outputs/flutter-apk/app-debug.apk`；需要实际界面验证时再用 `flutter devices` 和 `flutter run` 选择设备。单元及组件测试通过不等于学习通真实账号、通知投递和所有机型已验证。

Flutter、JDK、SDK 可安装在适合自己的位置，文档或历史记录里的维护者本机路径不是前置要求。`android/local.properties` 中的 `sdk.dir`、`flutter.sdk` 应由本机生成；工具链路径、IDE 缓存和个人环境配置不提交到 Git。

Windows 上若工程通过 `subst` 映射到独立盘符，而 Pub Cache 位于系统盘，Kotlin 增量编译可能出现 `this and base files have different roots`。先保留源码和 Pub Cache，使用一致的 Flutter/JDK/Android SDK 环境重试；仅在有明确证据时清理对应项目 `build/` 下的生成缓存，不要删除整个 Pub Cache。若本机 `local.properties` 指向不可用 SDK，优先在当前 PowerShell 进程设置 `ANDROID_HOME`、`ANDROID_SDK_ROOT` 和 `JAVA_HOME`，不要把机器路径提交到仓库。

Android Maven 依赖在 `CI=true` 时使用官方仓库，避免镜像故障阻断远端构建；本地保留现有镜像优先顺序。两种配置均不改变依赖版本。

## 从哪里读代码

| 位置 | 职责 |
| --- | --- |
| `lib/main.dart`、`lib/src/app/` | 启动、导航、主题和版本 |
| `lib/src/features/` | 首页、日历、统计、个人页等界面 |
| `lib/src/services/assignment_store.dart` | 同步状态、课程关注、提醒和本机记录协调 |
| `lib/src/local/` | 学习通请求、解析与本机持久化 |
| `lib/src/services/secure_session_store.dart` | 账号与密码的安全存储 |
| `android/app/src/main/` | Android 通道、访问验证、通知及小组件 |
| `test/` | Flutter 自动化测试 |

应用图标源码在仓库根目录 `art/app-icons/`。最终 PNG、自适应前景和单色资源由 `tool/generate_app_icons.py --candidate a|b --install` 生成；不要在桌面图标与课程线性图标之间复用含义不同的资源。

Android 8.0（API 26）及以上的通知必须先注册通知渠道。`LocalNotificationService` 维护 `assignment_deadlines`、`assignment_updates`、`daily_summary`、`personal_schedule`，在初始化阶段逐个检查并补建缺失渠道；已存在的渠道不重新注册，以免覆盖用户自定义名称。个人日程与每日摘要继续使用既有补偿式 `staging/committed` 通知事务；学习通截止事件迁移到应用私有 SQLite + AlarmManager，发送前由原生接收器重新校验账号代次、完成/隐藏/关注状态、时间窗口、截止时间与隐私设置。旧插件 `a:` 作业提醒先完成类别限定的取消迁移，新旧投递器不得同时生效；迁移不确定时暂停该账号作业自动投递并在体检中提示。原有摘要和个人提醒事务不能被简化为全局取消后重建。

学习通作业后台检查使用一个唯一的一次性 WorkManager 链。Worker 使用独立、不 `runApp()` 的 `backgroundMain` Flutter 入口，复用安全存储、学习通客户端、本地仓库和提醒规划；停止时取消网络并拒绝迟到提交。前台、Worker 和原生桥接共享进程内同步租约、写租约、账号会话代次与提醒 mutation version。SharedPreferences 与 SQLite 不是同一数据库事务，因此先标记快照待更新，完成仓库写入后以读取时的 mutation version 提交提醒快照；版本不符必须拒绝并重做计划。时间规则、监听过滤、稳定通知 ID 与数据库策略的 JVM 测试位于 `android/app/src/test/`，Flutter 规则与集成测试位于 `test/daytime_check_policy_test.dart`、`assignment_reminder_planner_test.dart` 和 `assignment_store_background_reminder_test.dart`。

Windows 原始工程路径若含中文字符，AGP 可能在配置阶段拒绝构建；`android.overridePathCheck=true` 只能绕过该前置检查，CMake 仍可能因生成路径 JSON 转义失败。可将当前工作树的 Flutter 工程复制到 ASCII 临时构建目录，在副本中配置 SDK/JDK 并构建；先确认副本包含当前全部源码、测试、资源与 Android 原生文件。Pub Cache 在 C 盘、工程在 D 盘时，Kotlin 增量编译可能出现 `this and base files have different roots`。本轮最终使用 `C:\campus-tools\build-work\chaoxing-journal-20261108-final-2` 同卷 ASCII 副本；`234` 是 `local_app` 子树内 Git 跟踪文件数，逐文件核对一致；此前构建输入扫描的 `255` 是另一统计范围（源码、测试、资源与 Android 构建输入），不是 Git 跟踪文件数。Gradle 属性未做临时覆盖，构建成功且未生成 Kotlin cross-root error log。Flutter 目标平台使用 `--target-platform android-arm64,android-x64`；`android/app/build.gradle` 排除全部 `lib/armeabi-v7a/**`，构建后运行 `python tool/check_apk_abis.py build/app/outputs/flutter-apk/app-debug.apk --abi arm64-v8a --abi x86_64`，确认没有引擎外 ABI 且两个目标 ABI 都包含 `libflutter.so`。不要删除整个 Pub Cache，也不要把临时构建配置写回共享工作树。

表中路径均相对于 Flutter 应用目录。修改同步逻辑时注意：读取失败不能被当作零作业；截止时间未知不能推断成无截止；本机隐藏不能写成学习通已提交；课程身份需区分课程与班级。

处理课程、截止时间或提交状态前，先读 [`client.py`](../../references/xuexitong-cli/xuexitong_mcp/client.py) 的 `fetch_homework`、`fetch_homework_detail`、`is_homework_pending`。列表的签名与详情链接各有来源；已提交/待批阅不等于未交，已截止未交仍需关注。Android 实现的最终行为以当前 Dart 代码和测试为准。

核对参考解析行为，可在参考目录中使用已安装依赖的 Python 环境运行：

```sh
python -B -c "import runpy; raise SystemExit(runpy.run_path('tests/run_tests.py')['run_all']())"
python -B -m xuexitong_mcp.cli hw-ls --help
```

环境准备与逐课查询见[参考目录 README](../../references/xuexitong-cli/README.md)及其 `pyproject.toml`。摘取部分的核心测试入口是 `run_all()`，独立桌面应用测试套件在上游；不要把摘取目录当成完整上游工作树。

## 安装身份与发布

截至 v1.6.3，debug 与 release 构建均使用 `com.example.studyassistant.journal`（基础 applicationId 加 `.journal` 后缀），沿用现有体验发布身份。调试密钥随构建环境而异，自己构建的 APK 不保证能覆盖体验包；相同包名也不能替代签名核对。历史基础包名 `com.example.studyassistant` 不代表当前 Release 的最终安装身份。

正式构建要求本机的 `android/key.properties` 和私有签名密钥；仓库不提供默认正式签名，缺少配置会阻止 release 构建。不要把密钥、口令、`key.properties`、账号、Cookie、APK 或设备数据提交到仓库。若维护发布渠道，必须先决定稳定的包名、密钥保管与升级迁移方案，再构建分发。

默认更新源是 `arrry-07/chaoxing-journal` 的 GitHub `releases/latest` API，仅使用正式发布。发布时增加 `pubspec.yaml` 与 `AppVersion` 的版本，使用 `vX.Y.Z` 标签，上传同签名、同包名的双架构 `chaoxing-journal-X.Y.Z.apk` 与 `SHA256SUMS.txt`。GitHub 返回的 APK `digest` 必须为有效 SHA-256；上传未就绪或缺失校验信息会拒绝应用内下载。相同显示版本的增量构建可用 `vX.Y.Z+版本码` 标签，仍须增加 Android versionCode；通常优先递增显示版本。

自定义更新源优先使用 `UPDATE_STABLE_MANIFEST_URL` 与 `UPDATE_MANUAL_MANIFEST_URL` 两个 HTTPS 清单：启动入口只接受 major/minor 提升，手动入口可发现最新补丁。旧 `UPDATE_MANIFEST_URL` 继续兼容为单清单。清单必须包含 `versionCode`、`versionName`、`applicationId`、`apkUrl`、`sha256`、`size`，可含 `notes` 和同摘要备用地址。未配置时直接使用 GitHub；配置主源后失败不会降级 GitHub。主分支提交、草稿和预发布不会被当作正式升级包。

更新任务由应用级 `AppUpdateController` 持有，弹窗与底部进度条只观察任务。新增入口需复用该控制器，避免关闭页面取消下载或创建重复任务；后台完成不自动打开安装器。原生安装前校验包名、签名、递增版本码、SDK 与 ABI，禁止为兼容测试绕过这些检查。系统终止进程后不保证继续下载。
