# 更新渠道与国内分发


## 当前版本与发布约定（2026-11-13 更新）

维护者最新要求覆盖旧的“小补丁仅手动提示”策略；下方旧规则用于解释历史客户端行为，不再约束新客户端必须静默。

- 小版本沿 `1.7.5 → 1.7.51 → 1.7.52 → 1.7.53` 递增；Android versionCode 独立递增，多个小问题合并一次。大范围改动先建议迭代版本，不擅自跳号。
- 开发中不反复升版；冻结候选后，版本号更新就对应一次正式 APK/Release，必须同步校验文件、版本记录与有效下载入口。纯文档变更不升版。
- 新客户端冷启动可以提示同主/次版本的新补丁；保留忽略版本与手动检查入口，不自动下载或安装。不能再以“补丁”作为禁止启动提示或必须非 latest 的理由。
- 必要测试、CI、原签名、完整性检查、草稿回下载与公开回下载仍须完成；旧 Tag/APK 不覆盖，不能仅修改源码版本声称已经发布。

### 实现与已发布客户端的区别

- `1.7.52+59` 迁移客户端默认读取 Gitee 固定清单：启动和手动检查优先使用 `update-manual.json`，有效主源结果不会额外请求 GitHub；主清单网络失败、无效或不可用时回退 GitHub 正式 Release。
- Gitee 清单中的 APK 主地址指向 Gitee Release，`backupApkUrl` 指向同一 GitHub Tag、同名 APK。两个地址共享大小和 SHA-256，APK 主源瞬时失败才会尝试 GitHub。
- 已发布的 `1.7.5+57` 及更早客户端仍执行旧启动门禁；首次升级可能需要手动检查或网页覆盖，改为 latest 不能绕过旧 major/minor 过滤。
- 已发布的 `1.7.51+58` 没有编入 Gitee 地址，无法远程切换；它可先通过 GitHub 更新到 1.7.52，之后的更新由新客户端使用 Gitee 主源。
- 国内同步使用 `scripts/gitee_release_sync.py`：校验 GitHub Release、APK 身份、签名、大小和 SHA-256，创建 Gitee Release、上传同名 APK、匿名完整下载复核，最后原子更新两份 JSON。
- 本轮执行与验收见[1.7.51 验收与发布记录](../reviews/2026-11-13-1.7.51近期体验修复验收与发布记录.md)和[执行方案](../plans/2026-11-13-近期体验修复执行方案.md)。

### 每日自动同步

[Gitee release sync](../../.github/workflows/gitee-release-sync.yml) 仅运行于 GitHub Actions：

- 每天北京时间 `03:17` 检查一次 GitHub latest，不跟随每次 Release 立即上传。
- 手动 `workflow_dispatch` 用于首次 seed 和失败恢复。
- Actions 只检查和发布清单，不再从云端上传 APK；最新版 APK 先由维护者在本机 Gitee 网页后台上传一次。
- 历史版本只核对 Gitee Release 和 APK 附件是否存在，不再从 Gitee 回头完整下载。
- 最新 manual 版本必须通过 Gitee 匿名完整下载和 SHA-256 校验后，才允许更新清单。
- 同一天重复运行时，若目标 Release 和 APK 已存在则复用；不会覆盖不同内容。
- Gitee 最多保留 3 个 APK Release，始终保护 stable、manual 引用的版本，并保留最新的第三个版本。其余旧 Release 删除，旧版本仍可从 GitHub 获取。
- GitHub 校验下载和 Gitee 最新版回下载发生在 Actions Runner；只有最新版 APK 的本机上传使用维护者网络。

首次 seed 前，先在 Gitee 网页后台创建并上传以下历史 APK，再通过 workflow_dispatch 执行，`tags` 填：

```text
v1.7.4,v1.7.5,v1.7.52
```

历史 `v1.7.4`、`v1.7.5` 只上传一次，不再由 Actions 回头完整下载。`v1.7.52` 作为最新 manual 版本仍执行完整回下载和摘要校验。

GitHub 仓库 Secret 仅需 `GITEE_TOKEN`。Token 在
<https://gitee.com/profile/personal_access_tokens> 创建并至少授予 `projects`
权限；不要写入仓库、清单、命令参数或日志。

### VPN/TUN 边界

日常只在本机上传最新一个 APK，历史版本不再重复上传或回下载，因此本机流量从整批历史包降为一个最新包。Actions 的校验下载不经过维护者本机网络。Android 或其他设备实际下载时是否经过 TUN，仍由设备上的 VPN 分流规则决定。需要直连时，应在 VPN 客户端将以下域名加入直连或分流规则：

```text
gitee.com
*.gitee.com
raw.giteeusercontent.com
foruda.gitee.com
```

应用不会自行修改系统 VPN、代理或证书策略。

## 历史发布规则（2026-11-10；被上方新约定取代）

- 本项目的小修通过必要验证后可直接Commit、Push、PR和发布APK，无需重复索取发布许可；不能绕过测试、CI、签名和完整性检查，不授权扩展业务或改变签名/仓库可见性。
- 当前1.6.7的小补丁从1.6.71+53开始，后续1.6.72等递增；较大迭代使用1.7.0等标准三段版本，提高主/次版本。版本名及Android buildCode须保持可升级，发布前检查占用。
- 小补丁正式公开但必须显式`--latest=false`，不弹启动更新、不显示更新横幅、不自动下载或安装；仅用户手动检查才提示。较大迭代才设latest，只有主/次版本提高才可启动提示，并尊重忽略版本。
- 自动检查使用`releases/latest`；新版手动检查以100条分页读取公开Release，排除草稿/预发布、选版本最高的候选。候选缺包、校验异常或分页失败须报错，不能回退旧候选假称成功。
- 严格静默首次切换：旧1.6.7自动和手动检查均只看latest，无法远程改变。1.6.71公开后仍保持latest=1.6.7，因此旧版首次只能网页下载；安装新规则客户端后手动检查才能发现后续非latest补丁。不得为了旧版手动发现而把小补丁设latest，也不得声称旧版已支持新规则。
- 旧Tag、APK和草稿附件不得覆盖；发布先草稿及回下载核验，公开时再次显式非latest并立即核对latest没变化。异常时撤回新Release为草稿，不移动Tag。
- 新发现的数据、安全或兼容性阻断必须先处理；已冻结限制准确披露，不自动标为通过。此规则适用于本项目，不套用到其他仓库。

## 旧发布客户端入口与优先级（不代表待发布分支）

App 保留两条检测通道：

- **GitHub 通道（默认）**：未配置任何清单时，启动检查读 `releases/latest`，手动检查分页读取公开 Release。APK 下载继续使用现有重试、首字节/总时限、大小和 SHA-256 校验。
- **国内主源**：构建时分别配置启动和手动清单，客户端直接访问主源，不先请求 GitHub：

  ```text
  --dart-define=UPDATE_STABLE_MANIFEST_URL=https://updates.example.org/update-stable.json
  --dart-define=UPDATE_MANUAL_MANIFEST_URL=https://updates.example.org/update-manual.json
  ```

路由规则：

1. 启动只使用 `UPDATE_STABLE_MANIFEST_URL`，即使清单错误地给出补丁，也只接受 major/minor 提升；同主/次版本的补丁返回“已是最新”，不弹窗、不自动下载。
2. 手动检查只使用 `UPDATE_MANUAL_MANIFEST_URL`，可以发现显示版本相同但 `versionCode` 更高的构建，也可以发现补丁。
3. 旧 `UPDATE_MANIFEST_URL` 继续兼容：该单清单同时服务启动和手动，但启动仍执行 major/minor 门禁。设置对应的双清单变量后，各自优先使用双清单入口。
4. 主源请求失败、返回错误或清单无效时直接报告失败，不降级到 GitHub、另一清单或其他未声明内容。没有配置对应清单时才使用 GitHub 默认通道。
5. “忽略此版本”逻辑不变：忽略只影响自动启动提示，用户之后手动检查仍可重新看到该版本。

## 清单契约

示例：

```json
{
  "versionCode": 55,
  "versionName": "1.7.3",
  "applicationId": "com.example.studyassistant.journal",
  "apkUrl": "https://updates.example.org/1.7.3-55/chaoxing-journal-1.7.3-55.apk",
  "backupApkUrl": "https://backup.example.org/1.7.3-55/chaoxing-journal-1.7.3-55.apk",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "size": 60123456,
  "notes": "发布说明"
}
```

客户端在提供更新前严格拒绝以下清单：

- 清单 URL、`apkUrl` 或备用地址不是无内嵌凭据的 HTTPS 直链。
- `applicationId` 不是精确的 `com.example.studyassistant.journal`。
- `versionName` 不是三段纯数字版本，或版本低于当前显示版本。
- `versionCode` 不是正整数、未高于当前安装的 versionCode，或超出 Android 可接受范围。
- `size` 不是正整数、超过下载上限，或缺失；默认上限为 256MiB。
- `sha256` 不是 64 位十六进制 SHA-256，或缺少 `apkUrl`。
- HTTP 200 返回 HTML、空白、JSON 数组或畸形 JSON。401/403、404、429 和其他状态分别保留错误语义，不会被当成“已是最新”。
- 清单响应上限为 64 KiB；清单主地址必须直接返回 200，不接受重定向，避免未签名清单被转移到未确认的页面。

清单请求附带 `Cache-Control: no-cache` 和 `Pragma: no-cache`。APK 发布路径必须包含唯一版本和 versionCode，不能覆盖旧文件；清单可以在下载文件通过公开回下载和哈希核验后再覆盖。

### 备用 APK 源

可用 `backupApkUrl`，或用 `backupApkUrls` 提供最多四个地址。所有地址共享清单中的同一 `versionCode`、`versionName`、`applicationId`、`size` 和 `sha256`，因此不存在“备用源另一份文件”被接受的情况。

- 只有连接失败、连接/接收/发送超时、HTTP 5xx 等瞬时网络错误才尝试备用地址。
- 主源返回 HTML、长度异常、摘要不符或包内容不符时立即失败，不会用备用源掩盖校验失败。
- 每次切换都建立新的临时目录，绝不拼接两个源的分片；完整文件仍须通过大小、ZIP/APK 头、SHA-256，再由原生安装前检查核验包名、签名、版本、SDK 和 ABI。
- APK 下载允许 HTTPS 重定向，但每一跳及最终地址都必须是 HTTPS；仅本机回环地址的测试服务器允许 HTTP。任何明文远程降级立即失败。
- 用户取消或总下载时限到点后不再尝试备用地址。现有进度、速度、重试和安装器复用同一 `AppUpdateController`。

## 生成清单

[`scripts/update-manifest.ps1`](../../scripts/update-manifest.ps1) 只生成并写入本地清单，不创建远端目录、不上传 APK 或清单。`-Channel` 必须选择 `stable` 或 `manual`。

手动清单示例：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/update-manifest.ps1 `
  -ApkPath artifacts/1.7.3-55/chaoxing-journal-1.7.3-55.apk `
  -VersionName 1.7.3 -VersionCode 55 -Channel manual `
  -PreviousVersionName 1.6.72 -PreviousVersionCode 54 `
  -BaseUrl https://updates.example.org `
  -OutPath artifacts/1.7.3-55/update-manual.json
```

稳定清单示例：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/update-manifest.ps1 `
  -ApkPath artifacts/1.7.3-55/chaoxing-journal-1.7.3-55.apk `
  -VersionName 1.7.3 -VersionCode 55 -Channel stable `
  -PreviousVersionName 1.6.72 -PreviousVersionCode 54 `
  -BaseUrl https://updates.example.org `
  -OutPath artifacts/1.7.3-55/update-stable.json
```

脚本会校验 APK/ZIP 文件头、版本格式、Android versionCode、HTTPS 基址和递增 code，并从文件计算大小及 SHA-256。它生成的唯一远端路径为：

```text
https://updates.example.org/1.7.3-55/chaoxing-journal-1.7.3-55.apk
```

使用 Gitee Release 时，可把 `BaseUrl` 设为 `https://gitee.com/<owner>/<repo>/releases/download`，并把唯一 tag 和附件名按上述 `版本-versionCode` 规则创建。对象存储、自有域名和 Gitee 都沿用同一 JSON 契约。

stable 和 manual 都强制提供上一发布版本及 versionCode，要求新 APK 的显示版本不倒退且 versionCode 严格递增；`-Channel stable` 另外拒绝补丁级清单。脚本通过 Android `aapt` 核对实际 applicationId/versionName/versionCode，并通过 `apksigner` 固定校验既有发布证书，任一不一致都拒绝生成清单。服务器仍须由维护者按发布策略拒绝直接用补丁覆盖 stable 入口；脚本不是远端访问控制。

## 历史双清单发布顺序（启用国内源前需按新约定复核）

1. 构建与现有正式包同包名、同签名、递增 versionCode 的 Release APK，核对实际 `applicationId`、versionName/versionCode、ABI 和证书。
2. 把 APK 上传到新的唯一 `版本-versionCode` 路径；先不覆盖任何旧 APK。
3. 关闭代理和登录态，从公开最终 URL 完整下载，核对字节大小、SHA-256、ZIP/APK 头和签名身份。只做 HEAD 或只下载前几字节不算完成。
4. 生成 `manual` 清单并上传，验证匿名获取、JSON、重定向、摘要和目标匹配。任何补丁都先只更新 manual。
5. 只有 major/minor 迭代才更新 stable 清单；补丁只进入 manual。GitHub latest 按维护者当前发布策略设置，1.7.51 已显式设为 latest；国内 stable 清单仍保持 major/minor 边界。
6. 在旧版测试包上执行启动、手动检查、忽略版本、取消下载、断网重试、完整下载、哈希/包名/签名失败和安装交接测试。

同一显示版本允许更高 versionCode 的手动补丁，但 APK 原生 versionCode 必须递增；安装前检查不能因清单通过而省略。

## Gitee 匿名直链核查（2026-11-12）

当前可用性证据仅来自公开、无凭据的只读检查：

- [Gitee 官方 Release 文档](https://help.gitee.com/repository/release/create)仍列普通单附件 100M、仓库附件总量 1G 等限制。当前正式包约 57.52MB，低于普通单附件门槛，但条款和限额应在正式采用时重新核对。
- 对一个公开 Gitee APK 发布页的匿名 HEAD 请求从 `https://gitee.com/droidvm/app/releases/download/v1.59/droidvm-1.59.apk` 经 `attach_files` 路由重定向到 `foruda.gitee.com/attach_file/...?token=...&ts=...`，最终返回 200、`Content-Disposition: attachment` 和 5,735,806 字节长度；该 APK 示例最终 `Content-Type` 为 `application/zip`。
- 对公开文本附件做 Range 请求返回了完整 200 响应，而不是明确的 206，因此不能假定 Gitee 支持分段/断点。当前客户端默认全文下载并校验，Range 不支持时也有安全回退测试，但不能把 Gitee 当作保证支持并发的源。
- 最终 `foruda.gitee.com` 地址含短时 token 和 `ts`，只能作为重定向结果，不能写进清单或长期缓存。清单应保存 Gitee 的公开 Release 路由。

结论：Gitee 当前匿名下载路由可以作为首个免费候选继续验证，但尚未用本项目 APK 上传、未实际下载本项目完整发布包，也未在中国大陆移动/联通/电信和家庭宽带上验证。开发机网络成功不等于全国可用，不能据此宣称“已上传”“已配置”或“国内更新已上线”。

## 托管状态与边界

- 当前没有生产 `UPDATE_STABLE_MANIFEST_URL` 或 `UPDATE_MANUAL_MANIFEST_URL`，没有维护者提供的 Gitee/COS/OSS/R2 桶、域名或发布凭据；本次没有执行上传、创建 Release、修改仓库可见性或正式签名。
- Gitee 匿名直链目前值得继续做正式包试验；仍需覆盖本项目 APK 的完整下载、重定向、限流/WAF、大陆多网络和每日可用性。失败时停止该候选，不通过拆分 APK 或修改后缀规避平台限制。
- 腾讯 COS、阿里 OSS 的新桶默认域名对 APK 分发有限制，通常还涉及自定义域名、备案、流量和请求费用，不能把免域名默认域名当作已可用方案。任何付费开通仍需具体报价和用户确认。
- 旧客户端无法通过新代码获得双清单能力。首次迁移必须提供可公开下载的国内页面或主源，并明确旧版不能自动发现新入口。
