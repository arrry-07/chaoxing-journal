记录时间：2026-11-19（Asia/Shanghai）。本文是评估与隔离验证清单，不生成新密钥、不签名、不替换正式包；签名变更由维护者另行批准。

## 现状

- `apksigner verify --verbose --print-certs`：v1 `false`、v2 `true`、v3 `false`、v3.1 `false`、v4 `false`；单签名者。
- 证书 DN：`C=US, O=Android, CN=Android Debug`；证书 SHA-256 `d36a571510e046dd196d7384f849f82b4fcff05ce3affb334765d5c752265d8a`；RSA 2048。
- 结论：当前是“Release 构建 + 体验/调试证书”的 v2 单签名包，没有 v3 谱系。它不是生产签名身份；公开包与私钥管理需要分开评估。

## 为什么不能直接换证书

Android 覆盖安装要求包名相同，且签名相同或落在可验证的轮换谱系内。当前安装包只有 v2 签名，平台没有记录 v3 谱系；直接在 v2 上换新证书会被系统拒绝。

应用内还有一层更严格的预检：`MainActivity.inspectApk()`（`study_assistant-1.1.0/local_app/android/app/src/main/kotlin/com/example/studyassistant/MainActivity.kt:301-336`）在 API 28+ 比较候选与已安装包的 `signingInfo.apkContentsSigners` 集合，在 API 26/27 比较 `GET_SIGNATURES` 集合。`apkContentsSigners` 只返回当前签名者，不包含历史证书；Android 官方要求需要历史时使用 `signingCertificateHistory`。因此：

- 系统可能接受带谱系的新签名包，但应用内预检会先以“安装签名不一致”拒绝；
- 只有先在旧证书下发布一个放宽预检的桥接版本，后续轮换包才能走应用内更新；
- API 26/27 不支持 v3，无法在这两类系统上完成证书轮换；只能继续旧证书，或在未来提高 `minSdk` / 要求重装。

## 官方机制

- APK Signature Scheme v3 支持带 proof-of-rotation 的密钥轮换；v3.1（Android 13/API 33+）允许在同一个 APK 中保留旧签名块，并按系统版本选择旧/新签名者。
- `apksigner` 的 `--rotation-min-sdk-version` 默认 33：Android 13+ 使用轮换后的新证书，Android 12L 及以下继续使用原证书。若应用已经在 Android 12L 或更低版本上用轮换后的证书签名，之后必须显式使用 `--rotation-min-sdk-version 28` 才能继续覆盖；这不是本项目首次迁移的默认路径。
- 首次迁移建议保持默认 33，避免在 API 28–32 上引入额外的平台差异；代价是这些系统继续使用旧证书，旧证书不能立即退役。

参考：[Android apksigner](https://developer.android.com/tools/apksigner)、[APK Signature Scheme v3.1](https://source.android.com/docs/security/features/apksigning/v3-1)、[SigningInfo.getSigningCertificateHistory](https://developer.android.com/reference/android/content/pm/SigningInfo#getSigningCertificateHistory())。

## 数据与备份

- 带有效谱系的系统覆盖安装保留应用数据；应用内预检只是前置检查，不是系统安装的最终权威。
- 若走“卸载后重装”（旧密钥丢失、谱系不可用或系统拒绝），应用数据会丢失。`AndroidManifest.xml` 的 `allowBackup=true` 只备份 `FlutterSharedPreferences.xml`（课业/设置），登录凭据和 WebView 状态需重新登录；应用内加密备份 `schema: 6` 是另一条恢复路径，需要口令、账号归属校验和兼容版本。
- 迁移前必须在隔离设备完成一次“导出加密备份 → 卸载 → 重装 → 恢复”的实际演练；不能用“Auto Backup 已开启”代替。
- 恢复后核对：登录态、课业记录、隐藏/关注、个人备注、计划、提醒规则与最近记录；提醒队列和系统通知不随备份自动恢复，需要重新计划。

## 建议顺序

1. **保持旧证书发布**：在维护者批准前，所有正式版本继续使用当前证书，不移动 Tag、不替换资产。
2. **桥接版本（旧证书）**：只修改 `inspectApk()` 的预检规则——API 28+ 接受“已安装证书出现在候选 `signingCertificateHistory` 中”的谱系，API 26/27 仍精确匹配；同时保留包名、版本号、ABI 和 pinned 证书校验。该版本必须先覆盖到现有用户，尤其是 API 33+。
3. **生成新密钥与谱系**：离线生成新 RSA 密钥，保存 `lineage` 与新旧密钥；不要复用调试证书口令，不要把私钥或谱系提交到仓库。
4. **构建轮换候选**：用 v3.1 谱系签名，默认 `--rotation-min-sdk-version 33`；`apksigner verify --print-certs` 必须显示 v3.1 与新旧证书历史。先做隔离设备矩阵，不直接公开发布。
5. **矩阵验证**：API 26/27（旧证书、系统安装）、API 29（旧证书、系统安装、应用内预检）、API 31/32（旧证书、通知/闹钟）、API 33+（新证书、系统安装、应用内预检、数据保留）。每档记录 `firstInstallTime`、登录态、数据计数、回拉 APK 哈希。
6. **决定旧证书退役条件**：若目标只是让 API 33+ 使用新证书，旧证书仍需为 API 26–32 服务；若目标是完全退役旧证书，需要提高 `minSdk` 或接受旧设备重装，并单独做迁移决策。

## 故障与回退

- 轮换包被系统拒绝：用户保留旧版本，数据不丢失；修复后用更高 `versionCode` 重新发布，不能降级覆盖。
- 应用内预检拒绝但系统可安装：不要让用户依赖手工安装；先修复桥接版本，再重新发布轮换包。
- 新密钥丢失：API 33+ 无法再签更新；必须保留离线备份。
- 谱系文件丢失：无法继续轮换；与密钥同等保护。
- 旧密钥丢失或疑似泄露：无法生成可信谱系；应转入“卸载重装 + 加密备份恢复”或新包名方案，并单独评估用户通知与数据影响。

## 本轮决定

- **短期**：继续使用当前证书，不执行轮换；本文不构成签名变更授权。
- **长期首选**：旧证书桥接版本 + v3.1 谱系 + 默认 `rotation-min-sdk 33`，让 API 33+ 平滑过渡，API 26–32 继续旧证书。
- **需要维护者另行批准**：新密钥生成、桥接版本代码变更、轮换包构建、任何正式包替换或公开上传。
