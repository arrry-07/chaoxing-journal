这份文档整理了对 chaoxing-journal 的产品、功能、UI/UX、Flutter 架构、学习通集成、数据安全、测试和发布流程的审查意见。它是后续 AI 编程工作的参考基线，不是要求 AI 一次性照单全收的改造命令。

最重要的执行原则：先重新读取当前仓库，再核实每条建议是否仍然成立；区分“当前仍存在的问题”“已经修复的问题”“有价值但尚未实施的建议”和“需要产品决策的方向”。不得仅凭本文件就直接重写架构或批量修改代码。

项目地址：https://github.com/arrry-07/chaoxing-journal

审查边界：此前分析基于公开仓库中的 README、主要 Dart 源码、Android 配置、隐私文档、Changelog、验收记录和 GitHub Actions 等材料进行静态审查。本文件不声称已经在本次生成时重新克隆仓库、运行 Flutter 测试、构建 APK 或完成安全渗透测试。仓库可能已经更新，所有版本号、测试数量、文件行数和问题状态都必须由执行 AI 重新确认。

## 一、执行摘要

产品方向建议：将应用从“学习通作业提醒工具”稳步发展为“以学习通为主要数据来源、同时支持个人任务的大学生课业管理工具”。不建议立即扩张为功能繁杂的校园超级应用。

当前最重要的竞争力不是 AI 功能或动画，而是数据可信、作业直达、提醒可靠、隐私克制和升级不丢数据。

- 数据可信：不确定的截止时间、提交状态、同步结果必须明确标记，不能猜测或伪装成功。
- 任务闭环：用户能快速看到待办、进入学习通对应作业，并清楚区分平台状态与个人进度。
- 长期可靠：账号隔离、备份恢复、接口变化适配、版本升级、通知和桌面组件都要有可验证的行为。
- 渐进式演进：先补齐数据与发布基础，再提升同步和交互，最后扩展个人学习管理能力。

建议优先顺序：P0 稳定与数据安全 → P1 同步可靠性和核心体验 → P2 学习管理扩展。

## 二、项目现状与已有优势

此前审查所见的产品能力包括：作业时间轴、截止日历、课程管理、完成情况统计、本地提醒、桌面小组件、学习通作业数据读取、作业详情跳转，以及应用内更新相关能力。具体功能是否仍与当前分支一致，应由执行 AI 逐项核对。

- 产品定位明确：围绕学习通作业、截止时间和提醒，用户价值容易理解。
- 有一定视觉识别度：纸张/手账风格、暖色系、手绘元素等设计方向值得保留。
- 已考虑复杂数据状态：部分成功、未知状态、截止时间读取失败等情况，不应被简单归并为“无作业”或“同步成功”。
- 已有工程化意识：此前仓库材料中可见测试、CI、开发文档、隐私说明、更新校验等工作。
- 学习通作业详情直达是有辨识度的核心能力，但必须持续验证不同版本、设备和作业类型的兼容性。

需要避免的误区：不要为了显得“专业”而无目标地引入 Riverpod、BLoC、Clean Architecture 或数据库；不要把历史审查中出现过的问题直接当成当前 Bug；不要把仓库验收记录中的测试数量当成此次重新执行的测试结果。

## 三、P0：先处理稳定性、数据安全和发布身份

### 1. 数据导出与恢复

这是最值得优先补齐的用户保障能力。建议支持 JSON 备份，至少覆盖课程、作业、本地隐藏记录、提醒规则和必要的用户设置。备份文件应包含格式版本、导出时间和校验信息。

- 恢复前先解析并展示预览：记录数量、账号归属、版本、冲突数量。
- 提供合并恢复和覆盖恢复两种明确操作；覆盖操作必须二次确认。
- 导出文件不得包含密码、Cookie、会话凭据、认证 Token 等敏感信息。
- 对可能包含签名参数或会话信息的作业链接进行脱敏，优先通过重新同步恢复。
- 为每个历史 schema 版本准备迁移测试；损坏文件应有可解释的错误和恢复路径。

### 2. applicationId、签名与升级迁移

此前检查发现 Debug 与 Release 的 applicationId 配置可能不同，体验包与正式包也可能使用不同签名身份。执行 AI 必须先核实当前 Gradle 配置、已发布 APK 的包名和证书指纹，再提出迁移方案。

- 确认最终 applicationId，并明确 Debug、Profile、Release 的命名策略。
- 确认长期签名密钥的保管方式；不得把 keystore、密码或私钥提交到 Git。
- 在 GitHub Actions 等 CI 环境通过 Secrets 注入签名材料。
- 评估现有体验包用户能否原地升级；若签名不兼容，制定明确迁移和数据备份说明。
- 在迁移方案验证前，不要擅自改包名、签名或发布配置。

### 3. 通知权限与锁屏隐私

建议把应用初始化与权限申请分开：应用可以先启动，等用户主动开启提醒或首次创建提醒时，再解释用途并请求必要权限。默认锁屏通知尽量只展示“有作业即将截止”，详细课程名和作业标题由用户主动选择是否展示。

- 核实 Android 通知权限、精确闹钟权限和各 Android 版本的行为差异。
- 默认采用更克制的锁屏可见性设置，提供隐私模式。
- 处理权限被拒绝、被系统撤销、精确闹钟不可用、设备重启等情况。
- 通知调度必须可恢复、可取消、可去重，避免同一作业重复提醒。

### 4. 数据状态准确性

所有不确定状态都要显式建模。平台提交状态、应用同步状态、个人完成进度是三种不同概念，不能混用。截止时间也要区分确认无截止、未开放、缺失年份、读取失败和无法信任等情况。

## 四、P1：同步可靠性与学习通适配层

### 1. 把学习通集成从业务页面中隔离

建议逐步形成独立 ChaoxingIntegration 层。课程、作业、考试、课堂活动、作业详情链接和响应解析应有清晰边界。学习通接口发生变化时，不应迫使日历、统计和提醒页面同步改动。

```text
integrations/chaoxing/\n  auth/\n  api/\n  adapters/\n    course_adapter.dart\n    homework_adapter.dart\n    exam_adapter.dart\n    activity_adapter.dart\n    assignment_link_adapter.dart\n  parsers/\n  models/\n  errors/
```

### 2. 建立接口样本与回归测试

使用经过脱敏的真实响应样本作为 fixtures，覆盖正常、空数据、部分字段缺失、接口结构变化、登录失效、安全验证、已提交、待批阅、无截止时间等场景。样本不得包含真实 Cookie、Token、个人账号或可复用的签名链接。

```text
test/fixtures/chaoxing/\n  course_list/\n  homework_list/\n  homework_detail/\n  submitted/\n  reviewing/\n  no_deadline/\n  verification_required/\n  schema_changed/
```

### 3. 请求性能与重试策略

此前代码审查提示部分课程和截止时间补充读取可能是串行请求。不要直接提高并发，而应先测量耗时，再做受控优化。

- 记录每门课程请求耗时、作业详情补充读取耗时和整体同步耗时。
- 对可缓存的课程信息、截止时间补充结果设置合理缓存与失效条件。
- 如确有必要，引入小并发请求队列，初始并发数可从 2～3 做设备和账号测试后确定。
- 对网络超时和部分 5xx 进行有限次数指数退避；对 401、403、安全验证和未知结构停止盲目重试。
- 保留部分成功结果，准确标记失败课程和数据新鲜度；不要因一门课程失败就丢弃全部成功数据。

### 4. 作业详情跳转的降级路径

详情直达是核心功能，但第三方 App、协议、版本和作业类型都可能变化。应按“精确打开对应作业 → 打开学习通课程/相关页面 → 展示可复制信息或提示用户手动查找”的顺序设计可解释的降级路径。不能只显示一个无反馈的按钮。

- 验证链接对应的课程、作业标题或稳定标识，避免打开错误作业。
- 处理未安装学习通、未登录、链接过期、协议不可用和目标 Activity 不存在。
- 兼容性记录至少包含学习通版本、Android 版本、设备类型、作业类型和验证结果。
- 不绕过平台验证，不自动答题或自动提交，不把非官方接口描述成稳定官方 API。

## 五、P1：架构与数据模型的渐进式整理

### 1. 不要一次性重写架构

此前重点关注的文件包括 assignment_store.dart、chaoxing_local_client.dart、local_assignment_repository.dart。执行 AI 应先确认这些文件在当前仓库中的实际位置、职责和依赖，再按业务边界拆分。文件行数本身不是重构理由，真正目标是降低职责耦合和回归风险。

### 2. 可逐步演进的目录结构

```text
lib/\n  app/\n    app.dart\n    router.dart\n    theme/\n  core/\n    network/\n    storage/\n    notifications/\n    errors/\n  features/\n    assignments/\n      data/\n      domain/\n      presentation/\n    courses/\n    calendar/\n    statistics/\n    reminders/\n    settings/\n  integrations/\n    chaoxing/\n      auth/\n      api/\n      parsers/\n      models/\n      deep_links/\n  main.dart
```

这只是目标结构示例，不要求立即照搬。应根据现有目录、依赖方向和测试覆盖率逐步迁移；迁移期间优先保持外部行为不变。

### 3. 状态模型规范化

如果当前模型仍使用自由字符串表达关键状态，可逐步改成 enum 或 sealed class，并提供旧数据兼容解析。建议明确区分平台作业状态、截止时间状态、同步状态和个人进度。

```text
enum AssignmentStatus {\n  pending, submitted, reviewing, graded, returned, unknown,\n}\n\nenum DeadlineState {\n  confirmed, noDeadline, notOpen, missingYear, readFailed, untrusted,\n}
```

注意：这是概念示例，实际枚举值必须以当前业务定义为准。需要处理未知服务端值，不能在解析失败时静默映射成 pending 或 submitted。

### 4. copyWith 对可空字段的清空语义

检查模型 copyWith 是否使用 value ?? oldValue 导致无法主动清空可空字段。若确实存在，应采用 sentinel、显式 clear 参数或其他一致方案，并增加回归测试，确保旧截止时间、原始文本等不会意外残留。

### 5. 本地存储何时升级 SQLite/Drift

当前若 SharedPreferences + JSON 仍能满足数据量和查询需求，不必为了“架构先进”立即迁移。出现多表关系、历史记录增长、复杂筛选、事务一致性或笔记与任务关联等实际需求时，再评估 SQLite + Drift。迁移前必须有备份、旧数据读取、迁移失败回滚和数据一致性测试。

## 六、P1：核心 UI/UX 优化

### 1. 保留手账视觉识别度

暖纸张背景、低饱和配色、手绘元素和现有品牌方向值得保留。不要为了追求所谓高级感，随意叠加大量渐变、玻璃拟态、装饰卡片或动画。

- 建立字体层级：标题可保留文楷风格；高密度正文、辅助信息优先考虑清晰易读的无衬线字体；数字使用稳定易辨认的数字字形。
- 统一日历、统计、课程管理和设置页面的间距、圆角、图标与状态颜色。
- 优化长标题、多行文字、大字号、系统字体缩放和小屏设备布局。
- 提供深色模式时，延续品牌色彩关系，不要简单反色。
- 加强 TalkBack、动态字体、触控区域和颜色对比度支持。

### 2. 首页信息架构

建议在现有时间轴基础上增加今日截止、未来 7 天、逾期等摘要；提供作业名和课程名搜索；提供今天、7 天内、逾期、待确认等快速筛选；展示最近同步时间和数据新鲜度。首页应先帮助用户回答“我现在要做什么”，而不是堆叠统计卡片。

### 3. 统计页面

逐步加入本周、本月、当前学期、全部等时间范围；展示各课程作业负担和完成趋势。只有在提交时间数据真实可靠时，才计算按时完成率。未知状态应单独展示，不能从统计中悄悄排除或当作已完成。

### 4. 桌面小组件

可以探索 2×2、4×2、4×4 等不同尺寸，分别展示最近一项、最近几项和待办列表。小组件应明确展示快照更新时间，提供点击进入对应详情的路径，并考虑隐私模式。小组件是缓存快照，不应让用户误认为它是实时同步数据。

## 七、P2：有价值的产品扩展

### 1. 个人学习记录

可在稳定性和核心体验完成后，加入个人备注、优先级、子任务、个人计划和学习时长等能力。必须把个人状态与学习通官方状态分开，例如“个人已完成”不能自动等价于“学习通已提交”。

### 2. 统一任务中心

未来可以逐步纳入考试、测验、课堂活动和手动任务，形成统一任务中心。建议先验证每类数据的来源、稳定性和用户需求，再逐类上线，不要一次性抓取所有页面。

### 3. AI 能力

AI 可以在后续辅助整理作业要求、拆分学习计划或总结个人笔记，但不应成为当前版本的优先事项。先确保数据准确、隐私边界清楚、核心提醒和跳转可靠。不要默认上传用户的课程内容或个人数据到第三方模型。

### 4. 跨设备同步

跨设备同步会引入账号体系、冲突解决、服务端成本、隐私政策和数据删除等复杂问题。只有当用户确实需要多设备一致性时再评估；在此之前，先做好本地备份与恢复。

## 八、测试、CI 与发布分发

### 1. 测试矩阵

| 测试层级 | 建议覆盖 |
| --- | --- |
| Dart 单元测试 | 解析器、状态映射、截止时间、时区、copyWith、数据迁移 |

| 真实设备测试 | 通知、精确闹钟、桌面组件、深链、后台限制 |
| 发布测试 | Release 构建、APK 签名、安装覆盖、升级迁移、架构匹配 |

### 2. CI 改进

- 确保 CI 运行格式检查、静态分析和 Flutter 测试。
- 按实际原生代码增加 Gradle/Kotlin 测试。
- 增加 Release 构建验证；签名 Secrets 缺失时可使用明确的无签名验证流程，但不得把测试包误标为正式包。
- 自动核对 pubspec 版本、Changelog、Git tag 和发布说明。
- 对关键解析器和数据迁移设定回归测试门槛。

### 3. 安装包分发

如果 GitHub 下载在目标用户网络环境中不稳定，可评估国内 HTTPS 镜像和按 ABI 分包。镜像清单需要版本、包名、架构、下载地址和 SHA-256；安装前仍需验证 APK 签名。不能仅凭 SHA-256 就认定发布者身份可信。

## 十、给 AI 编程工具的执行规则

- 先读取当前仓库的 README、目录结构、pubspec.yaml、Android Gradle 配置、CI、Changelog、隐私说明和核心业务代码。
- 先确认当前分支、工作区是否有用户未提交修改；未经允许不得覆盖、清理或重置用户改动。
- 逐条核实本文建议，标记为：仍存在 / 已修复 / 当前不存在 / 需要产品决策 / 证据不足。
- 每个判断都提供文件路径、类/函数/配置项和必要的代码证据；不要只给泛泛结论。
- 先输出审计报告和分阶段实施计划，不要立即改代码。
- 用户确认某个任务后，再一次只实施一个可验收的任务；每次修改前后运行相关测试。
- 优先做最小改动，保持现有功能、数据兼容和 UI 风格；不要无关重构。
- 涉及 applicationId、签名、数据迁移、网络协议、权限、用户数据删除和发布操作时，必须先说明影响并等待确认。
- 不把学习通非官方接口描述为稳定官方 API；不绕过验证，不自动答题或提交。
- 不编造测试结果、兼容性结果、性能数据或用户反馈。

### 第一阶段：只审计，不修改代码


## 十一、验收标准：什么才算真正完成

- 功能完成不等于页面能显示：必须覆盖正常、空数据、异常、权限拒绝和恢复场景。
- 数据功能必须有旧版本兼容、失败保护和可验证的数据一致性测试。
- 学习通集成功能必须说明支持的 App 版本、Android 版本和已验证的作业类型；未知环境应提供降级提示。
- 通知功能必须测试权限被拒绝、系统重启、重复调度、时区变化和锁屏隐私。
- 发布功能必须验证包名、签名、ABI、安装覆盖和升级路径。
- UI 修改必须检查小屏、大字号、长文本、深色模式（若支持）和无障碍。
- 所有测试结论必须来自本次实际运行，区分自动化测试、手工测试和静态检查。

最终原则：以用户数据安全和核心流程可靠为第一目标；每次只引入可解释、可测试、可回滚的变化。
