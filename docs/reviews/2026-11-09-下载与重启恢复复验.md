## 下载故障与修复

- 原失败是间歇性传输超时，不能据此断言 GitHub/CDN 永久不可达。旧公开客户端使用8/12秒请求策略；新候选只对 APK 请求使用30秒连接、60秒接收空闲时限，元数据策略不变，总下载上限仍为5分钟。
- Dio 5.9.2 的流空闲计时还存在“首部已到、首个正文未到”的窗口，新增传输封装在该窗口同样执行60秒上限，并把预读的首个非空数据块原样交还现有写入与校验流程。
- 只有正文开始前的连接/接收超时最多自动重试一次。首个 Range 探测的唯一重试可移除 Range，回退同一地址的既有完整下载路径；后续分段不重试。HTTP、证书、范围、长度、哈希错误均不自动重试。
- 每次尝试使用独立取消令牌，结束时主动关闭对应 HTTP 源；不把内部请求清理误报为用户取消，不消耗额外第三次尝试。取消、总预算及部分文件清理仍由原有流程约束。
- 没有引入新源、镜像、代理、登录逻辑或依赖。完整文件仍须通过原有大小、SHA-256 和 Android 安装身份校验。

## 重启恢复诊断

- 仅补齐 Manifest 缺少的通用 `android.intent.action.QUICKBOOT_POWERON`；接收器继续 `exported=false`。普通启动、包替换和 HTC 快速启动配置保留。
- 官方插件18.0.1要求的四种广播由安装后的 PackageManager 路由核对：旧48缺通用快速启动，新51四种路由均存在且接收器不导出。补齐快启不等于普通重启自动通过。
- 测试仅在新建标准 AVD 中执行，固定虚构身份与专用合成标记双重校验后才允许写入夹具。时间、个人记录均由现有 Dart 模型编码并回读；不手写偏好 XML，不读取真实账号安全存储。
- 每个样本独立ID，至少预留10分钟；保存排程、原生缓存、闹钟、kernel boot_id、解锁状态、开机前后日志和实际通知。排程后不运行会终止目标进程的 instrumentation。
- 中间普通候选 `1fc9880b8e9eeb52baf7a96782e67b0c46dcfdeddbe1d1467b1fa6f075aa8497` 的 API35 连续三次真实重启均通过，闹钟在首次解锁后自行恢复，无需手动打开应用；观察延迟均为1秒。它们属于该中间 APK，不能冒充最终 APK 的三次验收。
- API30 首次尝试期间模拟器及 ADB 在系统重启时无响应，证据保留为环境失败，不计作 App 通过或确定性产品缺陷。资源释放后的独立重验另列。
- API30独立环境的首个投递样本`qa-r03-api30-single-final-reboot-1794229260`仍未通过120秒窗口。实际断点是系统待机桶50（NEVER）、`standby_never_quota=0`：缓存和开机闹钟均存在，但`expectedWhenElapsed`已到，实际`whenElapsed`被推迟约24小时。这符合[Android11闹钟服务的零配额延后规则](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android11-release/services/core/java/com/android/server/AlarmManagerService.java)，不能写成接收器没有收到广播。
- 正常唤醒、解锁、打开App并操作导航后，待机桶自然由50变为10；没有设置待机桶、白名单、关闭省电或修改产品策略。首轮没有充分记录交互和重启前待机状态，不能仅凭这组证据把NEVER状态完全归因于某一条重启命令。
- 新样本在安排前核对实际界面交互及桶状态，使用系统框架正常重启路径（`svc power reboot`），仍强制验证kernel boot_id变化、完整启动、首次解锁和无手动打开App的排程恢复。系统重启导致连接中断时，仅记录命令确认丢失，后续必须独立证明真实重启；旧脚本在此处终止的失败case保留，不冒充通过。独立样本`qa-r03-api30-interactive-final-complete-1794230488`最终实际投递通过，观察延迟2秒，重启前后均为桶10。

配置依据为[插件18.0.1的Manifest说明](https://github.com/MaikuB/flutter_local_notifications/blob/flutter_local_notifications-v18.0.1/flutter_local_notifications/README.md#androidmanifestxml-setup)；省电样本间隔按[Android官方Doze限制](https://developer.android.com/training/monitoring-device-state/doze-standby)保留至少10分钟，不用连续密集触发推断提醒缺陷。
