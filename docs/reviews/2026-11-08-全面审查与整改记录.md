### 新增实际整改

| 问题 | 根因 | 本轮实现 |
| --- | --- | --- |
| 通知批量重排中途失败会破坏旧计划 | 原实现按固定通知 ID 逐条覆盖；第 N 条失败时前 N-1 条已替换，无法回滚 | `LocalNotificationService` 改为独立新 ID 批次 + 持久化 `staging/committed` 日志；整批安排成功才提交并取消旧批次。调度失败时补偿取消新批次；补偿或旧批次清理失败保留日志，初始化/体检重试恢复。插件不提供系统原子事务，故明确为补偿式可恢复，不宣称真正原子。 |
| 重启后事务可能留有不可见的部分提醒 | 之前没有持久化批次 ID 清单/事务阶段 | 新增每类别 active ID 清单和事务日志；启动自动恢复；体检显示待恢复状态并提供手动重试。ID 分配使用 2,000,000,000 以上的独立空间，避开历史作业/个人/摘要 ID 区间；隐私收紧也会清理已投递但仍在 active 清单内的 ID。 |
| 手动日程降级警告可能丢失 | Store 只汇总作业提醒异常，个人日程的精确闹钟降级 warning 没有被统一传递 | 每类批次错误保留具体原因，`_afterAssignmentsChanged` 汇总摘要与个人日程 warning；体检增加恢复状态及重试入口。 |
| 同步时间戳镜像写入失败被忽略 | `sync_attempt_at` / `sync_data_at` 写入结果未检查；同步报告可能错误显示完整成功 | 检查 SharedPreferences 写入 bool；失败后 reload 核对真实落盘值。镜像缺失时以 `sync_report_v1` 和仓库 `lastSync` 为 canonical 时间源；作业数据已写入但状态时间写入/最终报告保存失败时标记 partial 并展示原因。启动时协调 running/failed 报告与更新的数据仓库时间。 |
| 同步后的 Store 状态刷新失败可能误导 | 数据仓库已 merge 后，`_reloadJournal` / change-log 后续异常会被外层当成普通网络失败 | 增加持久化阶段异常处理；保留数据已写入的事实，报告转 partial 并提示重新核对，不把它说成完全成功。 |

### 通知事务与隐私清理

- Legacy v1 journal：`local_notification_service.dart:832-838` 在恢复前调用 ownership verify；`:874-884` 检查其他类别 active manifest ID 是否重叠，foreign manifest 不可读也 fail-closed；`:886-906` 同时检查 pending 与 active/delivered payload 的类别归属；`:908-915` 要求至少一个系统可见事务 ID 证明 journal 所属类别，否则保留事务记录。恢复主循环 `:681-724` 会阻断 foreign payload owner 类别的 orphan 扫描；`:730-788` 对 blocked category、foreign manifest collision 或缺失 manifest 保留通知，不做猜测性取消。
- Delivered active orphan：`hasPendingScheduleRecovery()`（`:401-441`）检查 pending 与 active；启动恢复（`:754-779`）也把 active/delivered orphan 加入扫描，manifest 可用且无 foreign collision 时写 staging journal 再补偿取消；manifest 缺失则 fail-closed。测试 `test/reminder_health_test.dart:1517-1562` 验证健康检查识别、active orphan 取消、旧 pending 保留及恢复后健康状态清除。
- 相关测试：v2 类别错位 `test/reminder_health_test.dart:1378-1419`；legacy foreign ID `:1421-1479`；v1 journal 与相邻 manifest 同时复制但无 OS 归属证据 `:1480-1516`；delivered orphan `:1517-1562`；journal 丢失/修复失败后的 pending orphan `:1861-1917`；损坏 journal `:1919-1968`。
- 隐私清理 `cancelPrivateSchedules()`（`local_notification_service.dart:65-170`）收集 pending 与 active/delivered private payload、manifest 和 journal ID；系统列表读取失败时保留有效元数据并报告不确定，取消失败或损坏 journal 不会被静默清理。`AssignmentStore.saveNotificationDetails(false)` 在持久化关闭详情前先完成旧通知清理，失败时不谎报隐私设置已生效；`_privacyCleanupPending` 会在后续刷新/重试继续处理。
- 结论：原两个 P2 的误取消 foreign ID 与漏检 delivered orphan 路径在当前工作树均已由 fail-closed 保护和测试覆盖，**无代码修改**。残余 P3：若合法 v1 journal 的所有 ID 已被 dismiss/removed，或 staging journal 的 ID 列表为空，类别证据无法重建，会持续 fail-closed 并要求人工核对；这是避免误取消的安全取舍。worker-1 建议的 payload-only foreign owner 独立测试可作为后续测试增强，不是已发现的生产缺陷。v1 schema 不存在于当前 HEAD，属于此前工作树中间态；设备是否运行过该中间构建未知。

### 同步、会话与账号隔离

- `AssignmentStore._syncAssignmentsBody()`（`assignment_store.dart:1014-1125`）先持久化 running 报告与 `sync_attempt_at`，再读取；`previousAssignments` 在全量同步前由当前账号正式/隐藏记录重建（`:1034-1040`）；数据 merge 完成后再写 `sync_data_at`，并 read-back 验证两个兼容时间镜像。写失败时报告 partial 和明确警告；最终报告持久化失败时保留内存 partial，不冒称已保存。
- `_reloadJournal()`（`:743-800`）用 repository 的 durable lastSyncAt 修复缺失/滞后的报告时间；中断在数据写入后但最终报告写入前时标为 partial 并说明数据已保存，不提升为完整成功。Store `_execute()`（`:1229-1265`）将异常转为 failed 报告并尝试持久化。
- `ChaoxingLocalClient.clearSession()`（`chaoxing_local_client.dart:283-298`）只清理 cookies、login payload、课程响应、请求/验证临时状态并递增 session generation；不无条件清空 `previousAssignments` / `trackedActivityIds`。真正账号身份变化在 `AssignmentStore.loginChaoxing()`（`assignment_store.dart:612-674`）清理通知、widget、web session 后清空旧账号追踪；logout（`:908-943`）显式清空。保留分层清理，旧请求由 generation guard 阻止回写。
- `previousAssignments` 在全量和单课程刷新前按当前账号数据填充；`trackedActivityIds` 当前仅被赋值/清空，没有生产读取点（只写状态），不据此做行数驱动重构；若未来需要活动 ID 差分，先确认真实调用方。
- 单课程读取、V3分页、截止时间补读均有 session generation 检查；此前 worker-4 已核对新增调用点无遗漏。当前未发现旧账号响应覆盖新账号状态的确定性路径。

### Repository、备份、更新与界面调用链

- `LocalAssignmentRepository` 使用 owner hash 与 switch checkpoint 保护账号数据；切换前备份旧作用域，切换/恢复失败时回滚，回滚失败保留 checkpoint；损坏数据在可恢复前不被默认覆盖。备份恢复按账号归属、schema、白名单和ID补缺，恢复前解密预览，恢复事务失败不删除唯一恢复证据。真实账号备份恢复本轮未执行。
