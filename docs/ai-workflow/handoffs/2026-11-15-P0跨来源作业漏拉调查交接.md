## 结论与本轮边界

**作业漏拉仍是未解决的最高优先级核心问题。** 用户明确反馈“很多作业拉取不到”；此前观察到“我的课程有多门、首页只有一条作业、主页还没刷新好”，且用户确认缺少的位置是首页而非“我的课程”。1.7.58 只修复了 HTML 签名作业详情缺年份时，利用同作业正式 API 的可信开始时间补全年份；它没有接入群聊、收件箱、IM、课程活动、考试或教务来源，也没有证明所有作业已覆盖。

- 本机显示会过滤：`study_assistant-1.1.0/local_app/lib/src/services/assignment_store.dart` 的 `formalAssignments` 按关注课程过滤，`visibleAssignments` 过滤已完成，`homeDisplayAssignments` 在预览时合并后继续按关注课程和未完成过滤；`study_assistant-1.1.0/local_app/lib/src/local/local_assignment_repository.dart` 的 `mergeAssignments` 和 `hiddenCompletedIds` 还会影响最终集合。因此“首页没看到”不等于“接口没返回”，也不等于“本机记录没有”。

## 未解决的用户反馈

用户当前说“很多作业拉取不到”，并明确“我的课程有多门，首页只有一条”“主页还没刷新好”。此前曾要求以“人工智能导论”收件箱/群聊遗漏样本对照。用户是学生账号，不能为了测试发布作业。该反馈与既有路线图 P0 一致，下一轮必须以真实使用现场为准，不能因一次样本中正式接口数量吻合而下结论说用户没有遇到漏拉。

“主页还没刷新好”还需单独区分：同步仍在进行、同步预览只展示了部分批次、同步结束但记录保存/显示过滤，以及刷新失败后沿用旧记录。把观察时间、同步阶段和结果一起记下，不要仅凭截图判断。

## 调查目标与阶段门

### 阶段 0：样本与只读工具准备

1. 核对现场账户与设备：只使用用户已登录的指定 MuMu“学习通”实例，不卸载、不清数据、不重新输入凭据；官方学习通侧只做用户允许的只读查看。
2. 准备脱敏采集表和本机只读取证入口。当前诊断可查同步详情中的 `issue.stage` 与 `issue.kind.name`、请求类别的成功/失败计数、关注课程与本地记录；**不序列化** `SyncIssue.message`、`courseKey` 或完整 `SyncReport` 到任何对外诊断，因为它们可能带真实课程/班级标识。诊断用受控 reason code、阶段和计数生成，不复制原始文本。
3. 无真实遗漏样本时到此停止。允许准备表单、只读对照步骤和受控诊断草案；**不猜测根因、不改解析、不接入新接口**。

### 阶段 1：逐来源、逐层面对照

对每一个“官方能看到、助手看不到”的具体作业，按同一时间窗口记录：

| 对照面 | 要确认的事实 |
| --- | --- |
| 官方课程作业页 | 是否出现在课程正式作业列表；课程、班级名称及作业标题；作业列表是否需要翻页或切换状态 |
| 官方收件箱/群聊/通知 | 是否只有消息提醒；消息是否指向正式作业、课堂活动、考试，或只是口头通知；是否存在无收件箱提醒的正式作业 |
| 官方课程活动/考试 | 是否位于与正式作业不同的入口和对象类型；是否真的需要作为“作业”呈现 |
| 本助手同步详情 | 本次同步时间、最终阶段、成功/失败课程数、结构化失败类别、请求类别计数；区分“未请求”“请求失败”“返回后未保存” |
| 本助手本机记录 | 关注课程列表、全部本地记录、隐藏记录、已完成记录、首页筛选/搜索偏好、同步预览是否结束 |
| 同步前后对照 | 清除筛选后手动完整同步一次；记录该样本在同步前、同步中、同步后的可见位置与计数变化 |

官方页面与消息的查看方式以用户当前客户端实际可用入口为准，不预设某个私有 IM 端点。官方课程作业页是判断“正式作业”的优先证据；消息本身先作为线索，不直接当作作业记录。

### 阶段 2：定位丢失层

把每个案例落到以下互斥或组合结论之一，并保留可复核证据：

1. **课程/班级未进入列表**：课程列表接口缺失、未关注、同名多班或班级身份不同。
2. **正式接口未返回**：官方课程作业页可见而当前正式接口只读响应无此条；检查身份参数、状态筛选、分页总数、时间窗口和登录会话。
3. **接口返回但解析丢弃**：响应中有对象，但解析器字段、状态、日期或类型过滤把它排除。
4. **保存/合并丢失**：同步预览或原始记录有对象，`mergeAssignments`、隐藏/完成状态或账号隔离合并后消失。
5. **本机显示过滤**：本地记录可见，但关注、隐藏、已完成、搜索/筛选或尚未结束的首页预览使其不显示。
6. **后台同步未触发或失败保留**：最近同步时间、阶段和失败类别与用户观察不一致，读取失败时显示旧记录。
7. **对象来自另一来源**：课堂活动、考试、教务或消息通知；需要另行判断产品是否应纳入，不能伪装成正式作业。
8. **纯群消息**：官方课程作业页没有对应正式作业；此时应先确认用户期望和产品定义，不把聊天正文变成作业数据。

### 阶段 3：根因确认后才提出实现

只有稳定复现、确定来源与合法只读访问方式、字段和身份可核对，并能说明去重与失败边界时，才提出模型/解析/后台修改方案。**开始实施前单独与用户确认范围与版本**；不要把本交接当成实现授权。

## 实现前置条件与验收口径

- 稳定身份：课程、班级、作业和消息对象都有可核对身份；同名多班不串课，跨来源能去重。
- 合法只读：使用当前登录会话可访问的官方入口；非官方 IM 只能作为默认关闭、用户明确同意后的补充，不绕过验证码或保存通知正文。
- 完整性：分页总数与逐页结果一致；状态筛选、跨年、明确不限、失败保留和账号隔离有边界。明确区分“读取失败”“未接入来源”“官方确实没有作业”。
- 语义：活动、考试、通知不得伪装成正式作业；截止年份与提交状态只来自可信平台证据。
- 验收至少覆盖 2–3 个真实遗漏案例闭环，并包含无收件箱提醒、官方课程页可见而助手不可见、同名多班、分页、状态变化和读取失败保留旧记录等适用场景。合成测试只能证明回归，不能替代真实案例闭环。
