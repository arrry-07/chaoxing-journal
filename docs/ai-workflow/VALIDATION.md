# 持续迭代与验证范围

本规则适用于长期维护中的开发、验收和正式发布。目标是让每项检查覆盖明确风险，并让有效证据跨步骤保留；开发中定向测试通过不等于正式包可以发布。

## 先确定本次终点

- **风险分档**统一读取全局 `staged-release-gate`（`C:/Users/Administrator/.gemini/config/skills/staged-release-gate/SKILL.md`）。文件数用于估算工作量。少文件涉及账号、存储、同步、时间、签名或跨模块契约时，按实际风险安排失败路径、调用方回归与独立审查。文案及低耦合机械改动可同窗完成，核对全部预期文件与终版 Diff。
- **Stage 1 开发与验收**在 `dev` 开展，按[集成验收流程](#集成验收与正式发布)确定本轮终点，验证改动并记录证据。涉及视觉设计时由 Gemini 4 核对设计方向，首个代表性页面可运行即做 [MuMu 早预览](../guides/开发与贡献.md#mumu-自测包)。代码契约审查独立判断行为与回归。每累积 1–3 个 `dev` 修订版或完成一个稳定阶段，可推进已授权的日常集成。
- **减少真机/模拟器反复刷接口**：涉及学习通请求跳过、归档、降级或解析边界的改动，先在本地用离线合成夹具把所有边界跑绿，最后在 MuMu 上集中做 1 次真实账号端到端刷新验证，避免高频刷接口反复触发 `9010` 验证码。
- 沿用现有包名与签名。公开 GitHub Release 会自动触发 Gitee 小索引更新。要求仅发 GitHub 时须先披露此联动；若明确禁止写入 Gitee，应在公开前解决冲突。独立手动写索引、推进 stable 或上传镜像 APK 须核对对应授权。仓库可见性、签名迁移、渠道策略调整和凭据或用户数据外传另行授权。
- 用一句话说明改动影响和准备运行的检查。范围明确时直接执行；只有新增耗时检查或扩大范围才补充理由，不为每条命令写计划。
- 同一交付范围使用一份简短清单，沿用当前任务记录或验收记录，不为每个 Git 节点、新消息或压缩重新建清单。

<a id="local-checks"></a>

## 开发阶段按影响选检查（本地快检）

- **纯文档、静态文案**：核对最终差异与受影响的链接。应用文案检查实际显示场景及受影响的文案断言、格式或资源校验。涉及布局或视觉设计时走代表页 MuMu 预览。流程文档要核对现行入口、命令和边界场景。
- **局部业务改动**：在 `local_app` 按范围做格式和静态分析，并用 `flutter test --no-pub --timeout 30s test/<相关用例>.dart` 覆盖改动行为。中文路径下用 `dart analyze <涉及的文件或目录>`。需要统一编排、仓库脚本回归或进程树超时时，用 `python scripts/verify_local_gate.py --tests <相关测试>`。这个入口仍包含 `dart analyze lib test` 与仓库脚本测试。
- **统一门禁的检查范围**：本地格式检查覆盖 `origin/main` 与当前 HEAD 的合并基线以来的改动、最近提交和本地改动；不同目标用 `--format-base <ref>` 指定。CI 的 PR 检查用合并提交的第一父提交，`main` 推送用事件的推送前提交。脚本默认单测超时 30s（`--test-case-timeout`），进程树超时定向 300s、全量 900s（`--flutter-timeout`），卡死时终止子进程并报告最后的用例。

触及主题、全局路由转场、公共组件、共享 Store 契约、更新或提醒策略时，须在 Stage 1 收口前对最终源码重跑本地全量门禁。审查或设备验收后的局部补丁须重跑受影响的测试、必要的设备场景；涉及上述共享契约或影响范围未明时补跑全量。日常集成 PR 和正式冻结 PR 前同样核对各自最终输入的全量结果，正式冻结额外启用 `--release`。三时区套件及完整 Android 矩阵仍由 PR、`main` 与 Tag CI 检查。

<a id="pwsh-utc-gate"></a>

### PowerShell UTC 门禁

在仓库根目录，用 PowerShell 7 设置子进程继承的 UTC 环境变量后运行检查。日常集成与全量开发验收运行以下两行。

```powershell
$env:TZ = 'UTC'
python scripts/verify_local_gate.py --mode full
```

正式冻结 PR 检查使用：

```powershell
$env:TZ = 'UTC'
python scripts/verify_local_gate.py --mode full --release
```

优先在独立的 `pwsh` 进程中执行，结束后退出该进程。同一终端后续启动的命令会沿用该环境变量。任一命令非零退出即停止对应门禁。

- **Android/Kotlin 本地一键缓存快检**：凡涉及 `android/`、Kotlin、Manifest 或通知渠道/后台桥接改动，Stage 1 与返工推送前统一执行 `python scripts/run_android_tests.py --local-fast`。脚本自动增量同步 `local_app` 至持久化 ASCII 缓存目录（复用 Gradle/构建缓存，免除重复 5 分钟冷构建）、按需离线 `flutter pub get` 并在其后重写转义 `android/local.properties`（根除 `[PropertyEscape]` 报错），一次性跑通 `:app:testDebugUnitTest`、`:app:compileDebugAndroidTestKotlin` 与 `:app:lintDebug`（可用 `--clean-cache` 重建缓存或 `--gradle-tasks` 指定子集），把 `androidTest` 编译漂移与 Lint 拦截在 Stage 1。

下面是定向回归起点，不是按文件后缀判断风险的固定套餐。涉及公共状态、跨模块依赖或影响范围不明时扩大定向回归，并说明依据。

| 改动 | 开发时先验证 | 扩大范围的信号 |
| --- | --- | --- |
| 文档、说明、工作约定 | 最终差异、相关链接；流程规则另检查场景和矛盾 | 命令、权限、发布顺序或 CI 行为变化不能只查拼写 |
| 局部 UI、日期标题和卡片 | 相关组件、排序不变、语义及受影响的窄屏/大字场景 | 共享控件、导航、筛选/排序逻辑变化扩大调用方回归 |
| 登录、同步、持久化、共享 Store | 原问题及失败边界。按影响检查取消/注销、旧数据保留、并发提交 | 账号代次、数据库、共享状态及解析变化需要集成回归，不能以代码少为由按低风险处理 |
| 截止时间、状态、提醒 | 分类边界、未知状态、相关日历/统计/提醒调用方 | 时间规则或时区处理变化补上海/洛杉矶等跨时区证据 |
| Android 原生、后台、Manifest/依赖 | `python scripts/run_android_tests.py --local-fast`（JVM 单测 + `androidTest` 编译 + Lint）及实际平台场景 | API 兼容、迁移、系统行为、依赖/工具链变化扩大真机/模拟器原生验证 |
| 更新源、清单、分发脚本或工作流 | 受影响的 Dart/Python/PowerShell/工作流契约与异常回退 | 版本身份、校验或安装边界变化补产物与更新路径验证 |

- 缺陷修复保留能复现原问题的行为回归，按功能模块就地维护契约测试，禁止按版本新建快照测试文件。高风险并发、回滚与安全修复移除目标防线后必须真实报红。保留有效旧回归，验证 Kotlin 行为时运行本地原生检查和正式发布 CI 矩阵，源码文本匹配不能代替编译或行为验证。
- 定向检查通过、当前需求已覆盖且无新风险时结束开发阶段的测试扩展。最终集成和发布仍按下面的范围执行。

<a id="dev-日常推送门禁"></a>

### dev 日常推送门禁

在本地 `dev` 完成改动、通过上述适用检查并提交后，直接执行轻量推送 `git push origin dev`（无需另行请示），并遵守四条门禁：

0. **状态与文档按阶段收口同步**：在每个阶段收口或中断交接提交时更新一次 [dev 本地状态](DEV_STATE.md)（已完成改动、基线或当前状态、下一步待办，只留最近 5 条），里程碑/自测打包/发版收口时同步更新 `PROJECT_STATE.md`；同一阶段内的中间小提交无需反复改写状态文件或为记录自身 SHA 追加空提交。只读调查在结束时留下结论与下一步。

1. **范围与安全检查**：推送前核对 `git status` 与本次提交 Diff，严禁将凭据、Cookie、账号响应、敏感日志、`docs/feedback/`、`scripts/demo-video/`、个人材料或 `.apk` 等大体积二进制产物纳入提交。
2. **分支与发版边界**：日常推送当前 `dev` 到 `origin/dev`。另按[两阶段门禁](#集成验收与正式发布)核对日常集成或正式发布的授权、差异与适用检查。
3. **回复末尾固定附带两行**：
   - 最新 `origin/dev` 提交号（完整 SHA 与简短信息）
   - GitHub 对比链接：`https://github.com/arrry-07/chaoxing-journal/compare/main...dev`（以及本次核心修改文件的 `dev` 分支直达链接）

<a id="版本号与迭代分级规则"></a>

## 版本号与迭代分级规则

- **格式规范**：所有正式版与 `dev` 自测包统一采用标准无前导零三段非负整数 `X.Y.Z+build`（Git Tag `vX.Y.Z`，禁止前导零及 `.01–.09`，不再使用 `-dev.N` 后缀；历史 `v1.8.01–v1.8.09` 仅由 `scripts/gitee_release_sync.py` 保留既有 Tag 兼容）。Android `versionCode`（`+build`）跨包严格单调递增，正式版构建号必须高于此前全部正式版与 `dev` 测试包。

| 递增位 | 适用场景与阶段 | 示例 | 同步范围与 Gitee 清单联动 |
| --- | --- | --- | --- |
| **修订号 `Z`**（`X.Y.Z → X.Y.(Z+1)`） | **`dev` 阶段自测与日常集成 PR**：较大阶段完成准备打 MuMu 自测包时升 `Z` 和构建号；每累积 1–3 个修订版可开日常集成 PR 合入 `main` 跑全量 CI | `1.92.0+132 → 1.92.1+133 → 1.92.2+134` | 版本字段同步 `pubspec.yaml` 与 `AppVersion`，验收结果写入 dev 状态；`README.md`/`CHANGELOG.md`/安装指南与 Gitee 清单维持当前正式版不变（仅在 Stage 2 更新）。CI 与本地默认传入 `--allow-dev` 仅对未标记的 `Z > 0` 预览包豁免正式文档；`Z == 0` 与含正式冻结标记的候选均强制核对；Tag CI 一律严格运行 `--tag`。 |
| **次版本号 `Y`**（由 `1.8.x` 跃迁至 `1.90.0`，此后每次正式版 `Y+1` 并归零 `Z`，**上限 `99`**） | **维护者明确授权正式发布后（Stage 2）**：下一正式版自 `1.90.0` 起步，此后升 `Y+1` 并归零 `Z`，在 `dev` 冻结后合入 `main` | `1.8.28 → 1.90.0 → 1.91.0 … → 1.99.0` | 冻结全套正式文档，自动更新 `update-manual.json`；仅大更新或紧急热修显式开启 `--promote-stable` 推进 `update-stable.json` |
| **主版本号 `X`**（`X.99.* → (X+1).0.0` 或重大跃迁） | **进位或跨代版本**：当 `Y` 已达 `99` 后下一次正式发版进位升 `X` 归零 `Y/Z`，或发生跨代重构/不兼容跃迁 | `1.99.0 → 2.0.0` | 冻结全套正式文档，自动更新 `update-manual.json`，大更新时显式开启 `--promote-stable` 推进 `update-stable.json` |

- **当前切换起点与命名防误解边界**：自 `1.8.26+120` 之后启用本规则；`dev` 上打 MuMu 自测包与合入日常集成 PR 均保持修订号 `Z > 0` 递增（`X.Y.Z+build`，严禁在正式发布前改用 `Z == 0` 的下一正式版号）。**在收到维护者明确正式发版指令前，`dev` 分支内的计划文件名、标题、交接、提交说明与进度描述一律使用当前/本轮 `dev` 修订号（如 `1.92.1`、`1.92.2`），严禁提前命名为下一正式版号（如 `1.93.0`）**，避免 AI 误以为已进入正式发版；仅在维护者明确下达正式发版指令进入 Stage 2 时，才将版本冻结并切换为下一正式版号（`Y+1` 归零 `Z`，构建号高于已用测试包），发布后下一轮 `dev` 自测包从该正式版第三位 `+1` 起步。纯文档变更、只读调研、方案编写、重复跑测或跨提交均不构成升版理由。

## 集成验收与正式发布

- 进入本轮最终集成验收时，重新读取需求、最终差异、调用方、测试和验收标准，并在集成输入上新跑必要的核心检查。代理报告、历史摘要和总测试数不能代替证据。
- 正式发布保留完整验收矩阵，包括全量 Flutter、分析、格式、元数据、时区和原生检查，以及 CI 和分发规则要求的检查。PR 前执行[本地 UTC 门禁](#pwsh-utc-gate)。三时区核心套件与 Gradle JVM、仪器测试编译、Lint 由 PR、`main` 和 Tag CI 承接。分发脚本变化运行对应检查。
- 先检查最终输入已有的原始日志和对应 CI：已覆盖且仍有效的检查不再手工复制一轮。本机与 CI 的平台/工具差异须明确；Linux 结果不能冒称 Windows 专项行为已验证。
- 必需 PR、main、Tag CI 仍核对各自最终提交的完整结果，不能拿旧提交绿灯替代；CI 因既定触发器运行全套不意味着本地也要再复制一套。完整 CI 由推送 main、正式版本 Tag、目标为 main 的 PR 与手动运行触发；日常 dev 推送不启动全量检查。其中 PR、`main` 与 `workflow_dispatch` 运行 `python study_assistant-1.1.0/local_app/tool/check_release_metadata.py --allow-dev`（仅对未标记的 `Z > 0` 预览包豁免正式文档），Tag CI 一律运行 `python study_assistant-1.1.0/local_app/tool/check_release_metadata.py --tag <tag>` 严格校验 Tag 名与全套正式文档一致。
- 版本在正式发布前统一冻结，按[版本号与迭代分级规则](#版本号与迭代分级规则)确定目标版本，日常小步集成进 `main` 不触发正式发布；测试每跑一轮、补一份文档或跨一个 Git 节点都不构成升版理由。
- 正式 APK 必须对应最终 main 的干净构建输入、锁定依赖、正常入口和原签名。打包后统一运行 `python scripts/verify_apk_and_report.py <apk> --expected-version <X.Y.Z+CODE>` 一次性核验大小、SHA-256、包名/版本/SDK、非 debuggable、双 ABI、16 KiB 对齐、ZIP CRC 与 v2 原证书指纹并生成标准 Markdown 验收段落（可附 `--write-sha256sums` 同步生成 `SHA256SUMS.txt`）。随后完成 MuMu 同签名覆盖、数据保留和实际改动验收，以及 GitHub 草稿认证下载与公开匿名下载验证。Gitee 小索引在 GitHub 公开后核验，失败须披露且不能声称双渠道完成，但不追溯阻断已满足门禁的 GitHub 发布。CI 的 Debug APK 不能替代正式 Release APK。
- 优先从最终 main 构建一次正式包；确需合并前候选来暴露风险时才增加候选。候选只有在全部构建输入（含版本、签名配置、参数和任何提交号派生元数据）与最终 main 一致、原始记录完整且文件哈希未变时才能绑定为最终包；否则从最终 main 重建。候选与最终证据分清，不追逐可复现哈希，也不复用旧版本 APK 冒充新正式包。
- PR 前检查需求/差异/暂存范围/相关证据；合并前核对最新 head、必需 CI、审查和授权；Tag/上传/公开前核对对应源码、产物、远端对象和阻断项。每道关卡核对当前对象，不重新启动整套验收。
- **两阶段推进顺序**
  - **Stage 1（开发、验收与日常集成）**。普通开发默认停在已验证并推送的 `dev`，留下终版差异、审查结论和证据。正式下载文档指向当前正式版。
    1. **做到发布前**。执行任务要求「做到发布前」时，授权包含创建或续用 `dev → main` 的日常集成 PR，以及跟进 CI 和审查。对待集成输入执行[本地 UTC 全量门禁](#pwsh-utc-gate)，通过 PR 前检查并推送后，创建或续用 PR。
    2. **PR 可合并**。跟进最新 PR HEAD 的全部必需 CI 和适用审查，排查失败、按需修复并核对新 HEAD 的结果。全部通过且满足适用的合并条件才算完成。汇报 PR 链接、HEAD、CI 和审查结论。仍有阻断时写明当前失败或缺证。
    3. **合入 `main`**。获合并授权后，核对最新 HEAD 的合并门禁，执行合并并验证 `main` CI `success`。正式版本冻结、Tag、Release 与线上更新索引进入 Stage 2 后处理。
  - **Stage 2（正式发布）**。仅在维护者明确下达正式发版指令、Stage 1 适用门禁通过后进入。业务源码与测试保持只读，仅允许冻结版本元数据及维护发布文档。发现代码或测试缺陷即停止发布，回 `dev` 修复、重审，并在最终输入上重跑适用检查。
    1. 在与 `main` 对齐的 `dev` 先新增目标版本的 `CHANGELOG.md` 条目，再运行 `python scripts/freeze_release.py --apply --mode formal --version <X.Y.Z+build>`。脚本默认探测上一正式版，也可用 `--previous` 明确指定。正式冻结将当前版本和构建号写入 `pubspec.yaml` 的 `# formal-release:` 标记，紧急热修同样适用。下一次用 `--apply --mode dev` 升预览版时自动移除标记。用[正式冻结 UTC 门禁](#pwsh-utc-gate)核对版本、正式文档与全量检查。紧急 Hotfix 从最新正式版 Tag 起步，发布后将修复同步到 `main` 与 `dev`。
    2. 冻结 PR 经审查及 CI 后合入 `main`。核对最终 `main` CI 后构建原签名双 ABI 正式包，完成 MuMu 保数据验收。
    3. 推 Tag 触发严格 Tag CI。等待期间可上传 Draft Release 资产并验证认证下载，Tag CI 成功后才可公开 GitHub Release 并设为 `latest`。公开后验证匿名下载、Gitee 索引和官网分发。正式官网派发缺少 Token 时明确失败，仓库 Release 与官网同步结果分别核对。已有 PR 优先续用，外部写入后读回真实对象。

- 正式冻结时在 `dev` 将目标版本设为下一正式版（自 `1.8.x` 跃迁为 `1.90.0+build`，此后按 `X.(Y+1).0+build` 递增，`Y` 已满 `99` 时设为 `(X+1).0.0+build`），同步 `pubspec.yaml`、`AppVersion`、`CHANGELOG.md`、`README.md` 与安装指南，构建号高于此前全部测试包。正式版发布后，下一轮 `dev` 自测包从该正式版的第三位 `+1`（如 `1.90.1+build`）起递增。
- PR、合并及 Tag／上传／公开前分别给出检查结论和证据位置。正式关闭时更新工程状态、反馈与验收证据，并按[发布收口与归档](../README.md#发布收口与归档)滚动维护。验证规则仅在门禁变化时更新。

## 协作与发布审读

- 只在独立勘察、互不重叠的实现或冻结差异的审查有收益时并行。先标明文件归属、依赖、共享接口、可写范围和验证要求。同一文件、构建缓存、输出目录与共享设备由一方负责；汇总方负责复核结果、更新状态及执行 Git 与发布操作。每方回报改动、证据、失败与缺证，适用的子代理同样遵循上下文读取矩阵。写改与审查禁子代理套娃，零文件交集并行由顶层总控扁平派发（仅跨 10+ 文件复杂执行任务可显式放行只读勘察孙代理）。
- **Gate 锚点**。初审核对从基线到待交付 HEAD 的完整差异。实质返工后复审同时传入上一轮审查 HEAD 到当前 HEAD 的增量、初始基线到当前 HEAD 的全量差异。前序已覆盖全量且返工范围明确时，复审聚焦改动、直接调用方和前序问题逐条核销。分窗、委派、返工与模型选型按全局 `staged-release-gate`。
- **审查提示词保持四要素留白**：给强推理审查/复审模型的提示词只写目标、事实源（Diff 锚点与真源文件）、硬红线（只读、禁止归档扫库、禁止再派子代理）与输出标准，不罗列死板检查清单、不附上游主观解释。
- 正式 Release 流程在 PR 创建或更新后，利用 CI、构建或设备等待时间委派至少一项独立只读审读（若当前工具支持）。围绕最终源码、项目状态、路线图和反馈台账检查缺陷、未验证项和下一轮优先级。无可用代理或代理超时时，由主代理自行复核并标明证据来源。
- 正式 Release 收口须完成审读并在交付中单列「发布后独立审读」，写明对象与 HEAD、是否阻断、本版发现、未验证项及下一轮优先级。

## 按每项检查的输入决定复用

| 证据 | 必须核对的输入或对象 |
| --- | --- |
| 测试、静态分析 | 实际读取的源码、调用依赖、测试/夹具、资源、依赖锁、命令和工具环境；依赖基线/暂存区的命令还需核对 Git 范围 |
| 构建 | 全部构建源码、资源、版本、锁文件、构建参数/环境和签名身份；输出文件存在且哈希一致 |
| 安装与实际运行 | 测试的 APK 哈希、设备/API、应用数据/权限状态和场景；状态变化时补验相关场景 |
| CI、Tag、Release、Gitee 索引 | 当前提交、Tag 指向、远端对象与状态；本地缓存不能证明远端当前可用 |

- 提交号只是定位符。只改无关文档或合并提交而检查输入字节未变，可查看原日志并记录差异依据后复用；业务调用依赖、测试、锁文件或工具环境变化，则重跑受影响项。不能只比较被修改的单个文件。
- 只在成功、原始日志完整、检查范围与输入可证实的情况下复用；日志缺失、执行期间输入变化、失败、超时和未覆盖项不能算通过。不清楚依赖影响时保守扩大检查，不猜测可复用。
- 现有缓存脚本按它实际实现的范围判定；本规则不改变缓存键，也不允许伪造指纹。缓存未命中时可以新跑，或另行明确说明经人工核对的旧日志复用，不能谎称工具命中缓存。
- 记录区分“本轮新跑”“核对后复用”“失败”“未验证/跳过”。同一范围后续节点不再以“进入最终验收”为名重复新跑；新增集成改动、失败或有效性疑问时才补验。

## 停止条件与长期维护

- 本版修复承诺、必需验证、CI、数据安全、签名和升级兼容出现失败或缺证时，停止对应的发布动作。范围外的已知缺陷、缺少自然样本或可选验证不足，经核对确实不影响本版验收和安全后，逐条列为下一补丁待办，继续完成当前补丁发布。
- 遗留问题逐条记录用户可见影响、当前证据或缺口、顺延原因及下一项取证或修复动作。发布说明、项目状态与对用户的交付回复都要披露，续接任务登记到已有[反馈清单](../待处理体验反馈.md)或路线图。合成、故障注入、自然观察分别标注；已发布的版本仍保留适用的未验证结论。
- 环境/网络失败后保留错误并检查状态，再选择有依据的重试、替代验证或报告阻断。反复尝试没有新证据就换方法；尝试次数不是产品门禁，也不是直接跳过检查的许可。外部写入超时先查对象，避免重复发布。
- 必需检查失败或缺证阻止其对应步骤，发布前门禁与发布后渠道核验不能混用；Gitee 索引失败只阻断双渠道完成声明，按项目约定重跑和披露。可选/不适用检查写明理由。MuMu 足以完成约定普通验收；真机、Doze、TalkBack 等缺口按当前范围和风险披露，不能机械阻塞所有版本，也不能把历史接受自动继承为本版已验证。
- 每次新增测试都应覆盖真实行为或失败边界；慢测、重复测试和环境脆弱项在实际反复拖慢时聚焦处理，不凭空新增“测试治理”工程，也不通过扩大 skip 或削弱断言提速。
- 阶段收口在 [DEV_STATE.md](DEV_STATE.md#工作流成效观察) 记录真实任务成效，复用现有 Git、CI 和会话证据。历史记录保留日期与适用范围。项目验证要求维护在本页，硬门禁以现有 CI 和发布规则为准。

具体命令见[开发与贡献](../guides/开发与贡献.md)，历史发布结果见[验收记录入口](../验收.md)。日常阶段按根 [AGENTS.md](../../AGENTS.md) 的 dev 流程推进。正式发布以维护者当次明确指令为准。
