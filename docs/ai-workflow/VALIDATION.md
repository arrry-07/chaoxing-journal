# 持续迭代与验证范围

本规则适用于长期维护中的开发、验收和正式发布。目标是让每项检查覆盖明确风险，并让有效证据跨步骤保留；开发中定向测试通过不等于正式包可以发布。

## 先确定本次终点

- **两段式分工与攒批发布**：常规功能修复与多问题排查优先先做只读会诊，将底层根因、涉及文件/行号与替换思路浓缩为原子级执行方案，再按方案集中施工；将同周期的 2–4 个独立问题合入同一个补丁版本走完一次 PR、CI、打包、MuMu 验收与正式 Release，避免每修一个小问题就反复触发全套发版流程。维护者明确要求紧急单点热修、候选预览或暂停停止线时，按当前边界执行。纯文档、只读调查和方案编写沿各自约定终点交付。
- **减少真机/模拟器反复刷接口**：涉及学习通请求跳过、归档、降级或解析边界的改动，先在本地用离线合成夹具把所有边界跑绿，最后在 MuMu 上集中做 1 次真实账号端到端刷新验证，避免高频刷接口反复触发 `9010` 验证码。
- 常规补丁沿现有包名、签名与 GitHub/Gitee 渠道推进，复用已给的授权。仓库可见性、签名迁移、渠道策略调整和凭据或用户数据外传另行授权。
- 用一句话说明改动影响和准备运行的检查。范围明确时直接执行；只有新增耗时检查或扩大范围才补充理由，不为每条命令写计划。
- 同一交付范围使用一份简短清单，沿用当前任务记录或验收记录，不为每个 Git 节点、新消息或压缩重新建清单。

## 开发阶段按影响选检查（本地秒级快检）

开发与施工阶段本地只执行**秒级定向门禁**：`flutter analyze --no-pub`、受影响的 `check_changed_format.py` 与**本次修改直接涉及的那 5–8 个 `test/*_test.dart` 文件**（以及按需执行的受影响脚本/原生单测）。不要在每次局部修改后于本地重跑 1500+ 全量 Flutter 测试与三时区套件；全量测试与三时区由 PR/main/Tag 的 GitHub Actions CI 承接。

下面是定向回归起点，不是按文件后缀判断风险的固定套餐。涉及公共状态、跨模块依赖或影响范围不明时扩大定向回归，并说明依据。

| 改动 | 开发时先验证 | 扩大范围的信号 |
| --- | --- | --- |
| 文档、说明、工作约定 | 最终差异、相关链接；流程规则另检查场景和矛盾 | 命令、权限、发布顺序或 CI 行为变化不能只查拼写 |
| 局部 UI、日期标题和卡片 | 相关组件、排序不变、语义及受影响的窄屏/大字场景 | 共享控件、导航、筛选/排序逻辑变化扩大调用方回归 |
| 登录、同步、持久化、共享 Store | 原问题及失败边界；按影响检查取消/注销、旧数据保留、并发提交 | 账号代次、数据库、共享状态及解析变化需要集成回归，不能以代码少为由按低风险处理 |
| 截止时间、状态、提醒 | 分类边界、未知状态、相关日历/统计/提醒调用方 | 时间规则或时区处理变化补上海/洛杉矶等跨时区证据 |
| Android 原生、后台、Manifest/依赖 | 受影响的 JVM/桥接/构建检查及实际平台场景 | API 兼容、迁移、系统行为、依赖/工具链变化扩大原生验证 |
| 更新源、清单、分发脚本或工作流 | 受影响的 Dart/Python/PowerShell/工作流契约与异常回退 | 版本身份、校验或安装边界变化补产物与更新路径验证 |

- 缺陷修复优先保留能复现原问题的行为回归；不为测试数量增加镜像实现的断言，也不删除有效旧回归来提速。
- 定向检查通过、当前需求已覆盖且无新风险时结束开发阶段的测试扩展。最终集成和发布仍按下面的范围执行。

<a id="dev-日常推送门禁"></a>

### dev 日常推送门禁

在本地 `dev` 完成改动、跑通上述秒级定向检查并提交后，直接执行轻量推送 `git push origin dev`（无需另行请示），并遵守三条门禁：

1. **范围与安全检查**：推送前核对 `git status` 与本次提交 Diff，严禁将凭据、Cookie、账号响应、敏感日志、`docs/feedback/`、`scripts/demo-video/`、个人材料或 `.apk` 等大体积二进制产物纳入提交。
2. **分支与发版边界**：只允许推送当前 `dev` 到 `origin/dev`，严禁顺手合入 `main`、创建正式 PR 或打正式版本 Tag（正式发版须等维护者明确指令）。
3. **回复末尾固定附带两行**：
   - 最新 `origin/dev` 提交号（完整 SHA 与简短信息）
   - GitHub 对比链接：`https://github.com/arrry-07/chaoxing-journal/compare/main...dev`（以及本次核心修改文件的 `dev` 分支直达链接）

## 集成验收与正式发布

- 进入本轮最终集成验收时，重新读取需求、最终差异、调用方、测试和验收标准，并在集成输入上新跑必要的核心检查。代理报告、历史摘要和总测试数不能代替证据。
- 正式应用发布保留当前完整验收矩阵：全量 Flutter、分析/格式/元数据、既定时区检查、原生检查，以及当前 CI 和项目发布规则要求的检查。其中 **全量 Flutter、三时区核心套件与 Gradle JVM/仪器编译/lint 优先交给 PR/main/Tag 云端 GitHub Actions CI 承接**，本地不机械复制一遍同一提交已被 CI 覆盖的全套耗时检查（仅在排查失败、CI 不可用或验证 Windows 专项行为时本地补跑对应子集）。分发脚本变化运行对应脚本检查。
- 先检查最终输入已有的原始日志和对应 CI：已覆盖且仍有效的检查不再手工复制一轮。本机与 CI 的平台/工具差异须明确；Linux 结果不能冒称 Windows 专项行为已验证。
- 必需 PR、main、Tag CI 仍核对各自最终提交的完整结果，不能拿旧提交绿灯替代；CI 因既定触发器运行全套不意味着本地也要再复制一套。完整 CI 由推送 main、正式版本 Tag、目标为 main 的 PR 与手动运行触发；日常 dev 推送不启动全量检查。
- 版本在范围收口后统一冻结，小问题按现有版本约定攒批合并发布；测试每跑一轮、补一份文档或跨一个 Git 节点都不构成升版理由。
- 正式 APK 必须对应最终 main 的干净构建输入、锁定依赖、正常入口和原签名。打包后统一运行 `python scripts/verify_apk_and_report.py <apk> --expected-version <X.Y.Z+CODE>` 一次性核验大小、SHA-256、包名/版本/SDK、非 debuggable、双 ABI、16 KiB 对齐、ZIP CRC 与 v2 原证书指纹并生成标准 Markdown 验收段落（可附 `--write-sha256sums` 同步生成 `SHA256SUMS.txt`）。随后完成 MuMu 同签名覆盖、数据保留和实际改动验收，以及 GitHub 草稿认证下载与公开匿名下载验证。Gitee 小索引在 GitHub 公开后核验，失败须披露且不能声称双渠道完成，但不追溯阻断已满足门禁的 GitHub 发布。CI 的 Debug APK 不能替代正式 Release APK。
- 优先从最终 main 构建一次正式包；确需合并前候选来暴露风险时才增加候选。候选只有在全部构建输入（含版本、签名配置、参数和任何提交号派生元数据）与最终 main 一致、原始记录完整且文件哈希未变时才能绑定为最终包；否则从最终 main 重建。候选与最终证据分清，不追逐可复现哈希，也不复用旧版本 APK 冒充新正式包。
- PR 前检查需求/差异/暂存范围/相关证据；合并前核对最新 head、必需 CI、审查和授权；Tag/上传/公开前核对对应源码、产物、远端对象和阻断项。每道关卡核对当前对象，不重新启动整套验收。
- 按顺序推进：本地集成验收 → 提交并推送精确范围 → 创建或更新 PR → 当前 head 的必需 CI 与审查 → 合并并核对最终 main CI → 绑定正式 APK 并通过设备验收 → Tag 及其必需 CI → 草稿资产完整回下载 → GitHub 正式发布 → 公开回下载与分发核验。已有 PR 优先续用。每次外部写入后读回真实对象。

- 正式冻结时同步 `pubspec.yaml`、`AppVersion`、CHANGELOG、README 与安装指南。正式版去掉 `-dev.N`，构建号高于所有预览包。下一轮预览从 `dev.1` 开始，构建号继续递增。
- PR、合并及 Tag／上传／公开前分别给出检查结论和证据位置。正式关闭时更新工程状态、反馈与验收证据，并按[发布收口与归档](../README.md#发布收口与归档)滚动维护。验证规则仅在门禁变化时更新。

## 协作与发布审读

- 只在独立勘察、互不重叠的实现或冻结差异的审查有收益时并行。先标明文件归属、依赖、共享接口、可写范围和验证要求。同一文件、构建缓存、输出目录与共享设备由一方负责；汇总方负责复核结果、更新状态及执行 Git 与发布操作。每方回报改动、证据、失败与缺证，适用的子代理同样遵循上下文读取矩阵。
- 正式 Release 流程在 PR 创建或更新后，利用 CI、构建或设备等待时间委派至少一项独立只读审读（若当前工具支持）。围绕最终源码、项目状态、路线图和反馈台账检查缺陷、未验证项和下一轮优先级。无可用代理或代理超时时，由主代理自行复核并标明证据来源。
- 正式 Release 收口须完成审读并在交付中单列「发布后独立审读」，写明对象与 HEAD、是否阻断、本版发现、未验证项及下一轮优先级。

## 按每项检查的输入决定复用

| 证据 | 必须核对的输入或对象 |
| --- | --- |
| 测试、静态分析 | 实际读取的源码、调用依赖、测试/夹具、资源、依赖锁、命令和工具环境；依赖基线/暂存区的命令还需核对 Git 范围 |
| 构建 | 全部构建源码、资源、版本、锁文件、构建参数/环境和签名身份；输出文件存在且哈希一致 |
| 安装与实际运行 | 测试的 APK 哈希、设备/API、应用数据/权限状态和场景；状态变化时补验相关场景 |
| CI、Tag、Release、Gitee 索引 | 当前提交、Tag 指向、远端对象与状态；本地缓存不能证明远端当前可用 |

- 提交号只是定位符。只改无关文档或合并提交而检查输入字节未变，可查看原日志并记录差异依据后复用；业务调用依赖、测试、锁文件或工具环境变化，则重跑受影响项。不能只比较被修改的单个文件。
- 只在成功、原始日志完整、检查范围与输入可证实的情况下复用；日志缺失、执行期间输入变化、失败、超时和未覆盖项不能算通过。不清楚依赖影响时保守扩大检查，不猜测可复用。
- 现有缓存脚本按它实际实现的范围判定；本规则不改变缓存键，也不允许伪造指纹。缓存未命中时可以新跑，或另行明确说明经人工核对的旧日志复用，不能谎称工具命中缓存。
- 记录区分“本轮新跑”“核对后复用”“失败”“未验证/跳过”。同一范围后续节点不再以“进入最终验收”为名重复新跑；新增集成改动、失败或有效性疑问时才补验。

## 停止条件与长期维护

- 本版修复承诺、必需验证、CI、数据安全、签名和升级兼容出现失败或缺证时，停止对应的发布动作。范围外的已知缺陷、缺少自然样本或可选验证不足，经核对确实不影响本版验收和安全后，逐条列为下一补丁待办，继续完成当前补丁发布。
- 遗留问题逐条记录用户可见影响、当前证据或缺口、顺延原因及下一项取证或修复动作。发布说明、项目状态与对用户的交付回复都要披露，续接任务登记到已有[反馈清单](../待处理体验反馈.md)或路线图。合成、故障注入、自然观察分别标注；已发布的版本仍保留适用的未验证结论。
- 环境/网络失败后保留错误并检查状态，再选择有依据的重试、替代验证或报告阻断。反复尝试没有新证据就换方法；尝试次数不是产品门禁，也不是直接跳过检查的许可。外部写入超时先查对象，避免重复发布。
- 必需检查失败或缺证阻止其对应步骤，发布前门禁与发布后渠道核验不能混用；Gitee 索引失败只阻断双渠道完成声明，按项目约定重跑和披露。可选/不适用检查写明理由。MuMu 足以完成约定普通验收；真机、Doze、TalkBack 等缺口按当前范围和风险披露，不能机械阻塞所有版本，也不能把历史接受自动继承为本版已验证。
- 每次新增测试都应覆盖真实行为或失败边界；慢测、重复测试和环境脆弱项在实际反复拖慢时聚焦处理，不凭空新增“测试治理”工程，也不通过扩大 skip 或削弱断言提速。
- 更新现有项目状态中的当前目标、源码范围、验证证据和下一步；历史记录保留日期与适用范围，不让旧版渠道/版本/授权指导新发布。规则和技能不按版本复制门禁清单；本文件维护项目验证范围，现有 CI/发布规则维护硬门禁，技能负责执行与证据复用。

具体命令见[开发与贡献](../guides/开发与贡献.md)，历史发布结果见[验收记录入口](../验收.md)。常规补丁发布按根 [AGENTS.md](../../AGENTS.md) 的默认授权和本轮范围执行；新增业务以维护者确认的方案为准。
