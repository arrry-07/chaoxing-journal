# 持续迭代与验证范围

本规则适用于长期维护中的开发、验收和正式发布。目标是让每项检查覆盖明确风险，并让有效证据跨步骤保留；开发中定向测试通过不等于正式包可以发布。

## 先确定本次终点

- 从当前任务确定是文档、局部开发、集成验收、打包还是正式发布；有发布技能不代表每次修改都进入发布。
- 用一句话说明改动影响和准备运行的检查。范围明确时直接执行；只有新增耗时检查或扩大范围才补充理由，不为每条命令写计划。
- 同一交付范围使用一份简短清单，沿用当前任务记录或验收记录，不为每个 Git 节点、新消息或压缩重新建清单。

## 开发阶段按影响选检查

下面是起点，不是按文件后缀判断风险的固定套餐。涉及公共状态、跨模块依赖或影响范围不明时扩大回归，并说明依据。

| 改动 | 开发时先验证 | 扩大范围的信号 |
| --- | --- | --- |
| 文档、说明、工作约定 | 最终差异、相关链接；流程规则另检查场景和矛盾 | 命令、权限、发布顺序或 CI 行为变化不能只查拼写 |
| 局部 UI、日期标题和卡片 | 相关组件、排序不变、语义及受影响的窄屏/大字场景 | 共享控件、导航、筛选/排序逻辑变化扩大调用方回归 |
| 登录、同步、持久化、共享 Store | 原问题及失败边界；按影响检查取消/注销、旧数据保留、并发提交 | 账号代次、数据库、共享状态及解析变化需要集成回归，不能以代码少为由按低风险处理 |
| 截止时间、状态、提醒 | 分类边界、未知状态、相关日历/统计/提醒调用方 | 时间规则或时区处理变化补上海/洛杉矶等跨时区证据 |
| Android 原生、后台、Manifest/依赖 | 受影响的 JVM/桥接/构建检查及实际平台场景 | API 兼容、迁移、系统行为、依赖/工具链变化扩大原生验证 |
| 更新源、清单、分发脚本或工作流 | 受影响的 Dart/Python/PowerShell/工作流契约与异常回退 | 版本身份、校验或安装边界变化补产物与更新路径验证 |

- 缺陷修复优先保留能复现原问题的行为回归；不为测试数量增加镜像实现的断言，也不删除有效旧回归来提速。
- 定向检查通过、当前需求已覆盖且无新风险时结束开发阶段的测试扩展。最终集成和发布仍按下面的范围执行。

## 集成验收与正式发布

- 进入本轮最终集成验收时，重新读取需求、最终差异、调用方、测试和验收标准，并在集成输入上新跑必要的核心检查。代理报告、历史摘要和总测试数不能代替证据。
- 正式应用发布保留当前完整验收矩阵：全量 Flutter、分析/格式/元数据、既定时区检查、原生检查，以及当前 CI 和项目发布规则要求的检查。分发脚本变化运行对应脚本检查；不要求每次局部编辑都本地重跑整套。
- 先检查最终输入已有的原始日志和对应 CI：已覆盖且仍有效的检查不再手工复制一轮。本机与 CI 的平台/工具差异须明确；Linux 结果不能冒称 Windows 专项行为已验证。
- 必需 PR、main、Tag CI 仍核对各自最终提交的完整结果，不能拿旧提交绿灯替代；CI 因既定触发器运行全套不意味着本地也要再复制一套。当前工作流对 push/PR 都触发，包括纯文档，本规则没有修改或绕过这一策略。
- 版本在范围收口后统一冻结，小问题按现有版本约定合并发布；测试每跑一轮、补一份文档或跨一个 Git 节点都不构成升版理由。
- 正式 APK 必须对应最终 main 的干净构建输入、锁定依赖、正常入口和原签名。保留身份/版本/SDK/ABI/签名/ZIP/对齐/哈希检查，MuMu 同签名覆盖、数据保留和实际改动验收，GitHub 草稿认证下载与公开匿名下载验证。Gitee 小索引在 GitHub 公开后核验，失败须披露且不能声称双渠道完成，但不追溯阻断已满足门禁的 GitHub 发布。CI 的 Debug APK 不能替代正式 Release APK。
- 优先从最终 main 构建一次正式包；确需合并前候选来暴露风险时才增加候选。候选只有在全部构建输入（含版本、签名配置、参数和任何提交号派生元数据）与最终 main 一致、原始记录完整且文件哈希未变时才能绑定为最终包；否则从最终 main 重建。候选与最终证据分清，不追逐可复现哈希，也不复用旧版本 APK 冒充新正式包。
- PR 前检查需求/差异/暂存范围/相关证据；合并前核对最新 head、必需 CI、审查和授权；Tag/上传/公开前核对对应源码、产物、远端对象和阻断项。每道关卡核对当前对象，不重新启动整套验收。

## 按每项检查的输入决定复用

| 证据 | 必须核对的输入或对象 |
| --- | --- |
| 测试、静态分析 | 实际读取的源码、调用依赖、测试/夹具、资源、依赖锁、命令和工具环境；依赖基线/暂存区的命令还需核对 Git 范围 |
| 构建 | 全部构建源码、资源、版本、锁文件、构建参数/环境和签名身份；输出文件存在且哈希一致 |
| 安装与实际运行 | 测试的 APK 哈希、设备/API、应用数据/权限状态和场景；状态变化时补验相关场景 |
| CI、Tag、Release、Gitee 索引 | 当前提交、Tag 指向、远端对象与状态；本地缓存不能证明远端当前可用 |

- 提交号只是定位符。只改无关文档或合并提交而检查输入字节未变，可查看原日志并记录差异依据后复用；业务调用依赖、测试、锁文件或工具环境变化，则重跑受影响项。不能只比较被修改的单个文件。
- 只在成功、原始日志完整、检查范围与输入可证实的情况下复用；日志缺失、执行期间输入变化、失败、超时和未覆盖项不能算通过。不清楚依赖影响时保守扩大检查，不猜测可复用。
- 现有缓存脚本按它实际实现的范围判定；本规则不改变缓存键，也不允许伪造指纹。缓存未命中时可以新跑，或另行明确说明经人工核对的旧日志复用，不能谎称工具命中缓存。
- 记录区分“本轮新跑”“核对后复用”“失败”“未验证/跳过”。同一范围后续节点不再以“进入最终验收”为名重复新跑；新增集成改动、失败或有效性疑问时才补验。

## 停止条件与长期维护

- 当前需求、必要回归及适用门禁都已覆盖，且没有未解决阻断项时收尾。无关问题进已有路线图或问题记录，不扩成当前任务。
- 环境/网络失败后保留错误并检查状态，再选择有依据的重试、替代验证或报告阻断。反复尝试没有新证据就换方法；尝试次数不是产品门禁，也不是直接跳过检查的许可。外部写入超时先查对象，避免重复发布。
- 必需检查失败或缺证阻止其对应步骤，发布前门禁与发布后渠道核验不能混用；Gitee 索引失败只阻断双渠道完成声明，按项目约定重跑和披露。可选/不适用检查写明理由。MuMu 足以完成约定普通验收；真机、Doze、TalkBack 等缺口按当前范围和风险披露，不能机械阻塞所有版本，也不能把历史接受自动继承为本版已验证。
- 每次新增测试都应覆盖真实行为或失败边界；慢测、重复测试和环境脆弱项在实际反复拖慢时聚焦处理，不凭空新增“测试治理”工程，也不通过扩大 skip 或削弱断言提速。
- 更新现有项目状态中的当前目标、源码范围、验证证据和下一步；历史记录保留日期与适用范围，不让旧版渠道/版本/授权指导新发布。规则和技能不按版本复制门禁清单；本文件维护项目验证范围，现有 CI/发布规则维护硬门禁，技能负责执行与证据复用。

具体命令见[开发与贡献](../guides/开发与贡献.md)，历史发布结果见[验收记录入口](../验收.md)。本规则本身不授权新业务、PR 合并、升版或发布。
