# Gitee 批量同步与长期路线图重排 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 降低 Gitee 镜像维护成本，同时保证每个正式包都完成 GitHub Release，并按软件定位重新排列长期任务优先级。

**Architecture:** GitHub 是每次正式包的必发源和完整发布档案；Gitee 是可选的低频批量镜像。同步 workflow 仅保留手动触发，不再每日运行或跟随每个 Release。长期路线图先解决作业拉取、截止可信度和提醒可靠性，再考虑新增数据源及可选扩展。

**Tech Stack:** Flutter、GitHub Actions、Python Gitee synchronizer、Markdown 文档。

**Spec:** 本文件以及 `docs/ROADMAP.md` 的 2026-11-14 优先级表。

## Global Constraints

- 每个冻结并递增版本的正式包必须在 GitHub 创建公开 Release、上传原签名 APK 和校验文件。
- Gitee 不做逐包发布；只在维护者明确指定的批量同步点运行。
- Gitee workflow 不得由 `schedule` 或 `release` 自动触发。
- Gitee 未同步时必须如实披露，不能阻止或替代 GitHub 正式发布。
- 未经用户明确要求，不修改 UI、布局、字体或视觉结构。
- 作业拉取、截止可信度、分页、身份匹配和提醒可靠性优先于可选扩展。

## Review Focus

- 发布新版后误以为 Gitee 必须同步，导致重复人工上传。
- 移除定时 workflow 后仍由旧文档或测试要求每日同步。
- Gitee 未更新时把 GitHub 正式版本误写成 Gitee 已同步。
- 路线图把 AI、云同步或视觉扩展排在作业数据核心问题之前。
- 版本升级只改文档而未完成 GitHub APK、校验和回下载证据。
