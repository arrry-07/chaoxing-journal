## 一、目标、最终规则与项目现状

### 1. 方案结论

当前产品方案可行，符合低打扰、低功耗的目标，但不能仅通过增加 WorkManager 和通知监听实现。

根据现有源码，必须同时解决以下问题：

- 当前自动同步由应用进程内 Timer 驱动，需要替换为系统后台调度。
- 当前截止通知由插件提前安排并直接投递，需要增加实际发送前的资格校验。
- 现有同步队列和通知队列不能协调多个 Flutter 执行环境，需要统一并发控制。
- 通知时区目前固定为 `Asia/Shanghai`，需要改为手机当前本地时区。

本方案保留现有 Flutter 业务、同步解析、账号数据和恢复机制，增加 Android 后台执行、账号级提醒状态及作业通知投递校验。

### 2. 最终产品规则

| 项目 | 最终要求 |
|---|---|
| 时间基准 | 手机当前本地时区 |
| 自动作业检查与通知窗口 | `[08:00, 次日00:00)` |
| 每日首次检查 | 08:00 为目标时间，不承诺准点 |
| 默认检查间隔 | 4小时 |
| 可选间隔 | 2、4、6小时 |
| 白天后台检查 | 新账号默认开启 |
| 通知监听 | 默认关闭，用户主动开启并授权 |
| 新增作业提醒 | 默认开启，仅正式作业 |
| 首次同步 | 首次完整成功同步建立基线，不集中提醒历史作业 |
| 完成状态 | 服务端确认完成或本机标记完成后停止提醒 |
| 隐藏、取消关注 | 不提醒 |
| 截止提醒 | 保留现有24小时及其他已保存规则 |
| 离线 | 保留缓存，继续符合条件的本机截止提醒 |
| 凌晨通知信号 | 仅记录待核对状态，白天处理 |
| 凌晨截止提醒 | 顺延到当天08:00，届时已截止则取消 |
| 批量新增 | 同一次检查发现多条时合并为一条通知 |
| 手动同步 | 全天允许；凌晨执行时仍不发送自动作业通知 |
| 发布 | 实施验证后提交、推送；不发布版本、不上传APK |

本轮补充确认：

1. 白天限制仅覆盖**学习通作业新增通知与截止通知**。个人待办、手动考试、每日摘要沿用原有规则。
2. 旧版关闭自动同步的账号继续关闭；原120/240/360分钟保留，其他正值迁移为240分钟。
3. 已确认新增、未完成但截止时间未知的作业允许新增提醒；文案显示“截止时间待确认”，不安排截止提醒。

白天后台检查开关控制定时兜底检查；通知监听开关独立控制通知触发核对；新增提醒开关只控制新增通知；截止提醒继续由原有规则控制。

## 二、技术架构与模块接口

### 1. 总体结构

```text
手动同步 / 前台恢复检查 / WorkManager / 学习通通知信号
                         ↓
                  统一同步协调入口
                         ↓
            现有学习通客户端 → 现有本地仓库
                         ↓
               账号级提醒状态与资格计算
                         ↓
          新增通知 / 截止排程 / 取消与恢复
                         ↓
             Android发送前校验 → 系统通知
```

采用以下职责划分：

- **Dart业务模块**：复用同步解析、合并、账号恢复和作业规则；生成提醒资格与计划。
- **Android后台模块**：WorkManager、通知监听、系统广播、无界面Flutter执行。
- **Android提醒状态模块**：持久化调度、去重、会话代次及发送所需的最小作业快照。
- **Android作业通知投递模块**：离线读取提醒快照，发送前重新判断账号、完成状态、时间窗口、规则和截止时间。

不把学习通网络协议复制到Kotlin，不启动常驻前台服务维持同步，不使用精确闹钟维持检查频率。

WorkManager采用唯一的一次性任务安排下一次检查，属于可延迟后台工作，不能保证08:00准点执行。[Android官方调度说明](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

### 2. Android后台执行方式

采用原生 WorkManager Worker 加无界面 FlutterEngine：

- 使用独立、保留的Dart后台入口，复用现有客户端与仓库。
- 初始化必要插件及业务依赖，不执行 `runApp()`。
- 不触发更新弹窗、权限申请、WebView验证码界面或可选头像资料请求。
- 公用桥接从仅依赖MainActivity的注册方式中提取，支持无Activity执行。
- Worker停止时取消网络请求，禁止迟到结果提交，释放执行资源。
- 安全存储尚不可用、设备尚未解锁时只延后处理，不清除登录态。

先验证无界面环境能读取现有安全存储和仓库，再接入真实调度。Flutter支持后台执行，但具体插件组合需要工程实测。[Flutter后台执行说明](https://docs.flutter.dev/packages-and-plugins/background-processes)

WorkManager依赖使用官方稳定版本并锁定；可先验证2.12.0与当前工程兼容。若存在构建兼容问题，选用官方仍满足当前工程的稳定版本，并在验收记录说明，不为此无关升级整套工具链。[官方版本记录](https://developer.android.com/jetpack/androidx/releases/work)

### 3. 统一同步接口

新增统一协调模块，向调用方提供：

```text
requestSync(reason, expectedAccount, expectedSessionEpoch)
    → SyncOutcome
```

`reason` 至少区分：

- 用户手动同步；
- 白天定时检查；
- 学习通通知信号；
- 前台恢复后的到期检查。

`SyncOutcome` 返回成功、部分成功、失败、合并执行、静默时段跳过、会话失效等结果，复用现有 `SyncReport/SyncIssue` 表达具体问题。

原有 `AssignmentStore.syncAssignments()` 保留为界面入口，内部转交协调模块。同步网络和合并逻辑从UI状态持有者中提取，避免创建完整页面状态来运行后台任务。

并发规则：

1. 同一账号同时只允许一轮同步网络流程；重叠触发合并。
2. 网络请求不长时间持有数据写锁，用户仍能标记完成、退出登录。
3. 提交前重新读取当前账号、持久化会话代次和最新本地状态。
4. 已切换账号、已退出或Worker停止的结果直接丢弃。
5. 合并时保留请求期间发生的本机完成、隐藏和关注变更。
6. 单课程刷新、网页返回核对、导入和备份恢复等相关写入也必须遵守统一写入协调。

### 4. 跨Flutter执行环境的写入一致性

现有 `_operations`、仓库 `_tail` 和通知静态队列仅在各自Dart环境内有效，不能作为新增后台环境的互斥保证。

实施方式：

- 所有相关Android组件运行于默认应用进程。
- 原生协调模块提供跨FlutterEngine的异步互斥与同步占用令牌。
- 数据修改、账号切换、提醒计划更新及通知发送使用同一协调机制。
- 获取写入权限后重新加载SharedPreferences，再读取、校验和写入。
- 通过令牌管理重入，避免仓库与外层协调重复加锁造成死锁。
- 引擎销毁、Worker取消和异常退出必须释放令牌；不允许凭超时直接让仍在执行的旧写入继续提交。
- 现有数据格式、损坏备份、账号归档与切换恢复继续保留。

新增提醒状态使用Android私有SQLite数据库，利用平台现有数据库能力实现事务与唯一约束，不迁移整个作业仓库。

SharedPreferences与SQLite之间不能形成同一个数据库事务，因此增加持久化变更标记：

1. 将该账号的提醒快照标记为待更新，暂停其自动投递。
2. 完成原仓库写入并校验。
3. 事务更新提醒快照、计划和变更版本，清除待更新标记。
4. 中途崩溃时依据原仓库与变更标记恢复，不使用不确定快照发送。
5. 仅在数据、提醒状态都可靠后向界面报告完整成功。

### 5. 账号级持久化状态

以现有规范化账号哈希作为账号标识，不在任务参数中放原始账号、密码或Cookie。

至少保存：

| 状态 | 用途 |
|---|---|
| 当前账号与持久化会话代次 | 拒绝旧账号任务和通知 |
| 检查开关、间隔、新增提醒开关 | 账号级配置 |
| 基线是否完成、基线作业集合 | 避免历史作业集中提醒 |
| 已发现作业集合、待提醒新增集合 | 区分真正新增与重复同步 |
| 待核对信号、信号版本 | 合并通知，避免同步期间的新信号被清除 |
| 最近尝试、数据成功、完整成功及失败原因 | 设置与体检展示 |
| 下次检查时间、调度代次、限流截止时间 | 后台恢复 |
| 作业提醒快照 | 当前完成/隐藏/关注/可信截止等资格 |
| 提醒事件、稳定通知ID、投递状态 | 去重与崩溃恢复 |

事件身份：

- 新增：`账号 + 规范作业ID + new`。
- 截止：`账号 + 规范作业ID + 提前分钟数 + UTC截止时间`。

同一作业重新标记未完成，不重新触发已经发送过的新增事件；未发送且仍有效的截止事件可以恢复。截止时间改变后形成新的截止事件。

事件状态至少区分待处理、已提交投递、已取消、已失效。不得把“已安排”记为“已发送”，也不得将系统通知提交成功描述为用户已看到。

## 三、业务与调度的具体实现

### 1. 白天检查算法

所有本地日期运算使用设备当前时区；持久化绝对时间使用UTC。

默认目标序列：08:00、12:00、16:00、20:00。

计算规则：

1. 当前在凌晨：安排当天08:00。
2. 当日首次检查尚未执行且当前已进入白天：允许一次到期检查，不补跑错过的多个时点。
3. 后续从本次实际检查开始时间加配置间隔。
4. 结果达到或超过次日00:00：改为下一日08:00。
5. 例如08:00任务延迟至09:10执行，4小时间隔下后续目标为13:10、17:10、21:10。
6. 通知触发核对不新建周期链，也不重置固定检查节奏；与临近定时检查重叠时复用同一轮结果。
7. 凌晨迟到任务跳过网络，重新安排08:00。
8. 网络执行前再次判断窗口；请求跨过00:00后不再启动后续课程请求，也不发送通知，已取得的数据可以安全保存。
9. 用户手动同步不受网络窗口限制；其新增提醒在凌晨只进入待处理集合。

调度要求：

- 使用唯一一次性Work链；不能用 `REPLACE` 取消正在执行的自身。
- 后继任务持久化与本次执行建立可靠衔接，防止进程中断后链路丢失。
- 不设置会让任务无限等待网络、导致下一次时间无法推进的设计；断网时记录本轮跳过并安排下一轮。
- 应用启动、登录完成、恢复前台、设备重启、应用升级、系统时间及时区变化时执行幂等调度核对。
- 已有唯一任务有效时不重复创建。
- 禁用后台检查后取消定时检查链，不影响独立启用的通知监听和缓存截止提醒。

失败不使用高频 `Result.retry()` 补偿。下一次自动尝试不得早于正常频率与服务端退避限制允许的时刻；次日08:00是正常日界目标，服务端 `Retry-After` 仍优先遵守。

### 2. 学习通通知监听

通过正式的 `NotificationListenerService` 接口实现，声明系统要求的绑定权限与服务配置。[Android官方接口](https://developer.android.com/reference/android/service/notification/NotificationListenerService)

处理顺序：

1. 检查应用内监听开关、系统通知使用权及当前登录账号。
2. 只接受实际安装的 `com.chaoxing.mobile`；不凭应用显示名称或模糊包名识别。
3. 忽略分组摘要、聊天通知及可明确识别的无关通知。
4. 通知正文只在内存中用于分类，不写入日志、数据库或诊断导出。
5. 持久化最小信号：账号代次、接收时间、去重摘要和可验证的作业标识。
6. 无法确认账号归属的通知不得据此直接发送具体作业提醒；只核对助手当前登录账号。
7. 凌晨只保存待核对标记，不启动网络。
8. 白天安排一次合并核对；同步期间新收到的信号提升版本，完成后只清除已消费版本。

默认采用60秒合并窗口；同一账号通知触发网络检查最短间隔10分钟。冷却期间的新信号继续保留，成功检查后不因重复通知再次启动同一轮；失败后交给正常定时检查或用户手动处理，不建立通知失败重试风暴。

直接提醒的门槛：

- 基线已建立；
- 标识能映射到当前账号已保存的规范作业；
- 已被同步流程确认属于新增；
- 本机资格有效且尚未发送。

未取得真实、脱敏通知样本前，默认走“信号→同步→确认新增→提醒”。不得猜测通知字段或通过相似标题匹配作业。

### 3. 首次同步与新增判断

首次基线建立条件：

- 当前账号的课程发现和作业读取完整成功；
- 无课程、分页、认证或影响结果完整性的失败；
- 仓库及基线状态均成功持久化。

具体行为：

- 基线未完成期间不发送新增通知。
- 部分成功可以更新成功课程，但不建立完整基线。
- 首次完整成功时，将当次及此前可靠保留的作业集合纳入基线，不补发历史新增。
- 升级旧客户端时先把已有缓存纳入已知集合，首次完整成功后完成新机制基线。
- 基线后按规范作业ID判断新增；已知作业状态变化、重新显示或重命名不属于新增。
- 部分同步中可靠取得的新作业可以提醒，但失败课程不能被推断为作业删除或完成。
- 基线历史作业仍参与未来截止提醒。
- 同一次检查的符合条件新增：一条打开详情，多条合并打开列表。

### 4. 提醒资格统一

两类作业通知共用基础判断：

- 当前账号与会话代次匹配；
- 正式作业身份可靠；
- 服务端状态确认未完成；
- 未被本机完成/隐藏集合排除；
- 所属课程仍被关注；
- 对应提醒开关或规则启用；
- 对应事件未发送、未取消；
- 当前在白天窗口；
- 持久化快照不存在待恢复变更。

新增提醒额外规则：

- 必须是基线建立后确认的新增。
- 可信截止已过则不提醒。
- 截止未知或不可信可以提醒，但不宣称剩余时间。

截止提醒额外规则：

- 必须存在可信、尚未过去的截止时间。
- 不直接放宽当前对截止读取失败的资格保护。
- 单纯断网不抹除上次有效计划。
- `now >= deadline` 即取消。

本机完成继续沿用现有隐藏集合语义，不在本轮重新设计“完成”与“隐藏”的数据结构。重新标记未完成只移除本机排除状态，不把服务端已提交作业改造成待提交。

### 5. 截止调度与实际投递

Android学习通作业截止通知改为“到时校验后发送”：

- Dart计算计划，Android持久化最小投递快照。
- 使用AlarmManager触发专用作业接收器；沿用现有精确提醒授权与非精确降级策略。
- 接收器只处理本地数据，不联网，也不启动完整Flutter界面。
- 发送前在统一协调保护下重新读取资格、事件、当前时间及隐私设置。
- 文案依据实际发送时间重新计算剩余时间。
- 低频后台同步继续使用WorkManager，不使用闹钟维持检查频率。Android对两类调度有不同定位。[官方闹钟说明](https://developer.android.com/develop/background-work/services/alarms)

时间处理：

```text
原提醒时间位于00:00—08:00
    → 顺延到该日08:00
    → 若届时已截止，取消
    → 否则按实际剩余时间发送
```

若多个规则顺延到同一时刻，同一作业合并为一次通知，并记录对应规则已消费。不同截止版本的旧事件必须失效。

迁移与恢复：

- 原有插件安排的学习通作业通知必须先完成可恢复迁移。
- 沿用现有归属证明、独立ID、staging/committed和补偿恢复原则。
- 新旧投递器不能同时发送同一事件；迁移状态不明确时暂停该账号作业自动通知并在体检中提示恢复。
- 不触碰个人日程和每日摘要的原有排程。
- 新增通知渠道、作业原生计划及活动通知必须纳入隐私清理、退出取消和健康检查。
- 完成、隐藏、取消关注、关闭规则时取消待发事件及仍显示的相关通知。
- 重启后依据持久化事件恢复；恢复过程本身不重新发送已完成事件。

系统通知提交与数据库写入之间无法实现绝对原子操作。使用稳定通知ID、可恢复投递记录及只提醒一次的通知配置，恢复时先核对活动通知，避免重复声音；不得宣称端到端严格“恰好一次”。

### 6. 账号与异常处理

账号切换：

1. 先提升持久化会话代次，使旧任务失效。
2. 取消旧账号待发及当前显示的作业通知。
3. 按现有仓库机制完成归档与切换。
4. 恢复目标账号的配置、基线和去重记录。
5. 重建目标账号有效任务。

退出登录清理待核对、待发提醒和活动通知；不得为保留提醒历史而改变现有退出清理用户数据的行为。

备份恢复后根据恢复的作业重新构建提醒快照，不恢复旧Worker实例、系统通知ID或过时待发队列。新增本机运行状态不得作为可移植任务备份。

| 情况 | 处理 |
|---|---|
| 断网 | 保留数据，记录结果，缓存截止提醒继续 |
| 认证失效 | 复用现有认证判断；确认失效后暂停后台网络，等待前台重新认证 |
| 验证码 | 记录需用户处理，不在后台启动验证界面 |
| 部分课程失败 | 合并成功数据，失败课程保留缓存 |
| 限流 | 遵守既有请求退避，并持久化跨轮次限制 |
| Worker取消 | 停止请求，拒绝迟到提交，恢复后核对调度 |
| 监听权限撤销 | 停止通知信号处理，定时检查继续 |
| 通知发送权限拒绝 | 不提交通知，不标为已发送；恢复权限后重新核验，合并处理 |
| 提醒状态损坏 | 保留原始记录，暂停不确定投递，提供可见恢复入口 |

### 7. 设置、权限和点击

沿用现有页面，不新增独立设置体系：

- 提醒设置：后台检查开关、固定窗口、2/4/6小时间隔、通知监听、新增提醒。
- 同步状态页：最近尝试、结果及可理解的失败原因。
- 提醒体检：通知发送权限、监听权限、下一次目标检查、待核对状态、调度/迁移恢复问题。
- 同步页删除原15/30/60分钟及任意分钟输入，避免出现两套冲突配置。

权限必须由用户主动操作触发。通知使用权说明系统授权范围及本应用只处理学习通作业信号的行为；系统授权状态与应用开关分别展示。Android 13及以上正确处理 `POST_NOTIFICATIONS`。[官方权限说明](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

点击通知采用内部事件标识解析账号和目标：

- 一条作业打开现有详情，多条打开作业列表。
- 账号不匹配时不自动切换账号、不展示旧账号详情。
- 作业已完成时显示当前状态，不恢复旧提醒。
- 作业不存在时返回列表并提示。
- 不通过给现有深链随意添加查询参数绕过当前严格校验。
- 锁屏详情继续遵守现有隐私偏好。
