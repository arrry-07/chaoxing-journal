## 1. 修复跨午夜与账号作用域的检查续接

本阶段使已经收到的信号在窗口延后和身份变化时有明确执行入口。

### 1.1 调度确认合同

本阶段先冻结并实现完整 v6 schema，包括本节的 `notification_attempts` 与阶段 2 的 `reminder_history`、`reminder_schedule_evidence`，再开发行为。首次安装和直升路径使用同一建表定义，避免阶段间安装相同版本但不同 schema 的候选。

新增内部结果 `NotificationEnqueueResult`，取值为 `confirmed`、`notNeeded`、`failed`。`failed` 包含已知失败与确认超时，二者保留独立原因码。

后继确认接收 `accountHash`、`expectedSessionEpoch`、`currentWorkId` 和可空的 `claimToPreserve`。领取后的延后使用该 claim 的版本，即使当前没有新的 claimable 版本，也继续检查或创建后继。已有任务只有在属于同一账号／epoch、具有持久队列记录并且 ID 有别于当前 Worker 时，才构成后继证据。

WorkManager Operation 完成并不独立证明 KEEP 创建了新任务。入队后重新读取对应作用域的 WorkInfo。确认同一个有效后继即可；重复回调及确认超时重试均采用幂等策略。

### 1.2 完成时的决定

保留及时、唯一、未 stopped 且 `success=false && skipped=true && skipReason=outsideWindow` 的条件，另由 claimed 阶段或已持久的未调用远端回执证明安全释放。完成回调以一个原子终态对象发布结果，保证结果内容先于完成信号可见。

| 当前结果 | 数据操作 | Worker 结果 |
| --- | --- | --- |
| 领取前因窗口／冷却延后，后继已确认 | 保留未领取信号 | success |
| 领取前延后，后继确认失败或未知 | 保留未领取信号 | retry |
| 已领取、收到合格 outsideWindow、后继已确认 | 执行原有 token CAS 回退 | success；CAS 拒绝后按最新状态收尾 |
| 已领取、收到合格 outsideWindow、后继失败或未知 | 仍以同一 token 执行 CAS 回退，当前持久 WorkSpec 承担退避 | retry |
| epoch／token／阶段变化或该版本已消费导致 CAS 拒绝 | 重新读取当前作用域状态；更高未尝试版本需要后续载体 | 后续载体未确认时 retry；已失活／已消费／已由其他尝试接管时 success |
| 已开始远端同步后失败、超时、取消或迟到回调 | 使用现有尝试记账；只为更高未尝试版本收尾 | 常规业务结果 success；补排失败时 retry 仅驱动队列维护 |

退避使用 WorkManager 指数退避，初始 10 分钟、采用平台上限。同一 WorkSpec 重试入口先核对当前身份、窗口、冷却和最新 claimable 版本，再决定是否创建 FlutterEngine。已经尝试过的版本受数据库原子领取保护。入队确认未知但实际成功时，多个载体同样依赖该领取合同去重。

释放 CAS 的条件固定为当前账号 active、listener enabled、epoch/token/attempted/claimedAt/ownerWorkId 匹配、持久阶段为 claimed 或 windowDeferred、`pending >= claim.version` 且 `priorConsumedVersion <= consumed < claim.version`。保留最新 pending 和 consumed，只恢复 priorAttemptedVersion/priorLastSignalCheckAt 并清理本次 token 与尝试行。完整 pending/consumed 快照相等条件由这一合同替代。更高 claim 使用新 token，旧 claim 无法释放它。

覆盖一个具体反例，claim=7、prior consumed=5，另一有效同步把 consumed 推进到 6。此时版本 7 仍可安全释放，pending 若已经增到 8 也应保留 8 并释放当前未授权尝试。

当前 Worker 从 CAS 回退到返回 retry 之间崩溃的场景，需要验证 WorkManager 对未完成 WorkSpec 的恢复。系统停止、用户禁用监听、退出与身份轮换仍通过当前作用域及 token 防护收尾。数据库写入故障使 CAS 无法确认时，重读持久尝试确认状态，当前 WorkSpec 进入退避；claimed 行使下一次执行能够再次验证并释放。

`scheduleNotificationCheck` 与 `scheduleNotificationFollowUpIfNeeded` 统一返回上述结果。Worker 收尾据此选择队列维护退避。通知监听器没有当前 Worker 可复用时，保留数据库 pending 信号、记录入队失败，并由现有启动／恢复／系统变化入口再次核对。

### 1.3 持久尝试与远端许可

新增 `notification_attempts`，每个账号最多一行。列为 account_hash 主键、session_epoch、claim_token、owner_work_id 可空、claimed_version、claimed_at、prior_attempted_version、prior_last_signal_check_at 可空、prior_consumed_version、phase。phase 取 claimed、remoteAuthorized、windowDeferred 或 settled。claim 的账户更新与尝试行写入同一事务。现有 claim 方法增加可选 ownerWorkId，原 Long? 包装可继续调用；自动进程恢复只接管有明确 WorkSpec ID 的行。

后台通知 payload 带入 claimToken 和 workerId，Store 以本次同步操作的不可变上下文传递。ownerWorkId 使用 Worker.id，leaseOwner 的每次随机 UUID 继续服务租约。新增严格桥接 `authorizeNotificationRemoteStart(accountHash, sessionEpoch, claimToken, workerId)`，返回 granted、outsideWindow 或 stale。它核对当前 token、owner、epoch、active/listener 及实时窗口，再将 phase 原子置为 remoteAuthorized；确认后 Dart 才能执行该操作的课业远端读取。存储／桥接异常向调用方明确失败。

授权位于会话初始化／租约等待之后、紧邻首个课程／活动／作业／考试远端读取的位置，并复核实际当前时间。使用不可变 `NotificationRemoteStartContext` 传递 token/WorkSpec ID；后台 run 参数和 Store 内部同步链路一并接入。授权返回 outsideWindow 以现有结构化 skipReason 传播，异常进入明确错误路径。逐项追踪会话恢复及客户端惰性初始化，所有课业读取均由该门槛覆盖。手动、白天和前台核对触发继续沿用自己的同步合同。

重试／进程恢复时，只对同一个 WorkSpec ID、同账号／epoch/token 且 phase=claimed 的尝试恢复旧 claim，再执行窗口预检和最新版本领取。remoteAuthorized 表示已给出远端许可，使用已尝试语义。授权确认后、实际请求前消失仍属于结果不确定的真实边界，记录 unconfirmed，由后续正常同步核对。

Dart 在许可返回后、实际客户端读取前复核时间。本次不可变同步结果增加 remoteReadInvoked，它只在调用客户端之前置为 true，字段缺失使用未知语义。及时唯一的 outsideWindow 回执若明确为 false，由 Worker 核对 token/owner 后持久转为 windowDeferred，再按同一 CAS 释放。windowDeferred 与 claimed 一样可由同一 WorkSpec 恢复。许可已授予但该回执尚未持久化即消失时，继续保留 unconfirmed 边界。

正常结束但不属于窗口释放路径的尝试持久转为 settled。超时和 onStopped 也尝试结算该 token，使迟到的远端授权被拒绝。remoteAuthorized／settled 均可被更高版本的原子领取替换。迟到结算需核对 token 与 WorkSpec ID；当前拥有者已经变化时返回 stale。此举防止为队列维护重试同一 Worker 时，把已明确结算的前置业务失败当作崩溃恢复。

释放、消费到该版本、账号失活／轮换及更高领取会清除或替换对应尝试行。v5 原有 token 没有阶段证据，迁移保留原记账，作为既有未知尝试处理。该表属于核心调度状态，其持久化错误使用核心错误路径；历史表的尽力写入适用于阶段 2 的记录。

### 1.4 队列作用域与取消

通知唯一任务名固定为 `notification_assignment_check:<accountHash>:<sessionEpoch>`，日间任务使用 `daytime_assignment_check:<accountHash>:<sessionEpoch>`，各自增加同作用域 tag。窗口和冷却采用手机本地时区的现有规则。

- 调度、状态查询、后继确认、监听开关及取消均使用作用域对象。
- 用户主动切换账号或主动重新登录前捕获旧作用域，成功认证产生新的原生 epoch，旧任务只能取消旧名字／tag。
- 同账号的用户主动重新登录也产生新 epoch。重复启动的 `ensureActiveAccount` 和后台 `_refreshChaoxingSession` 登录态初始化沿用当前 claim 的作用域。
- 更新旧会话时使用 `expectedSessionEpoch` 验证，晚到的旧设置、退出清理或取消请求不能针对新作用域生效。
- `clearActiveAccount` 调用方带出原始清理作用域，失败续清也保留该作用域；新账号及新 epoch 使用自己的队列名字。
- 对旧全局名称 `notification_assignment_check` 和 `daytime_assignment_check` 的取消只覆盖两个旧名称。取消后核对当前设置及 pending 信号，重新建立当前作用域载体。
- 同作用域继续采用排队 KEEP、运行中追加唯一后继、运行且已有后继时合并的策略。
- 现有 `cancelAllForAccount(Context)` 改为显式作用域取消接口，桥接和失败续清调用方全部传递原始 scope。日间 Worker 的 payload 也保存 expected epoch，收尾、nextCheckAt 写入及后续日间排队均按相同 scope 验证。陈旧 Worker 收尾只触发当前活跃 scope 的重新核对。
- WorkInfo 的归属使用上述 unique name/tag 与应用保存的作用域核对；现有 Android WorkInfo 未提供输入 Data 读取接口。

## 2. 提醒记录的存储与桥接合同

本阶段使近期操作能够跨进程重启查询，同时保持有界数据量。

### 2.1 数据库 v6

新建 `reminder_history`。列固定如下，时间单位统一为 UTC epoch 毫秒。

| 列 | 类型及用途 |
| --- | --- |
| id | INTEGER PRIMARY KEY AUTOINCREMENT，稳定游标 |
| account_hash / session_epoch / history_generation | TEXT / INTEGER / INTEGER，账号、业务代次、历史代次 |
| observation_id / operation_sequence | TEXT / INTEGER，调用重试幂等键和原生分配的操作序号 |
| subject_kind / subject_id | TEXT / nullable TEXT，assignment、manual、summary、account |
| logical_key | TEXT，逻辑提醒身份，使用现有事件 ID 或下述构造 |
| category | TEXT，newAssignment、deadline、examStart、personal、summary、backgroundCheck |
| stage / reason_code | TEXT / nullable TEXT，固定枚举 |
| observed_at / scheduled_at | INTEGER / nullable INTEGER，事实发生时间及该阶段目标时间 |
| notification_id / batch_key | nullable INTEGER / nullable TEXT，仅本机关联 |

索引覆盖 `(account_hash, history_generation, id)` 和 `(account_hash, history_generation, logical_key, id)`。`observation_id` 唯一索引使用账号与历史代次限定。

新增行采用追加式写入。原生事件复用 eventId；个人逻辑键由事项 ID 与提前 30 分钟后的目标毫秒组成；摘要逻辑键使用摘要目标毫秒；后台检查使用信号版本及触发原因。原始业务 ID 通过模型解析取得。每次实际操作取得一次 operationSequence，观察 ID 由 historyGeneration、operationSequence 和该操作内固定的观察 ordinal 构成，重试沿用同一 ID。

有效观测均持久化为独立行，相同 observationId 的重试确认原行。连续相同结果在页面显示时折叠，不通过丢弃幂等凭据实现去重。内部批次重排仅更换数值 ID、业务排期未变化时，更新当前证据映射；真实失败、恢复、延后和业务状态变化形成观测。

每个账号记录 prunedThroughOperationSequence，保存在历史控制文件。裁剪前先持久化本次将移除观测的最大操作序号，再在历史写事务中裁剪与插入。已有同 ID 行优先返回 duplicate；ID 已不存在且 operationSequence 不高于该账号裁剪水位时返回 expired。故障使水位领先于实际裁剪时，已存在的行仍可确认，新到的旧操作按过期处理。裁剪后的超时重试因此无法重新插入旧结果。

先删除本账号 observedAt 早于当前时刻减 30 天的行，再保留最新 500 条。时间回拨时仍执行条数上限。页面折叠连续项时按底层行游标续页。保留期按 observedAt，条数限制按稳定 id；当前有效排期证据保存在独立表。

v6 同时覆盖 onCreate 和旧库直升。v3、v4、v5 测试夹具应包含全部原有表和非空数据，验证快照、事件、信号、token、attempted/consumed 和迁移标志保留。

| acquireReminderObservationContext | accountHash、sessionEpoch | 当前可用上下文，或明确 unavailable 原因 |
| appendReminderObservation | context、observation | inserted、duplicate、expired、stale、unavailable 中的一种 |
| recordReminderScheduleOutcome | context、批次逐项结果 | 当前证据映射的更新结果及历史记录结果 |
| listReminderHistory | 当前读 context、snapshotMaxId 可空、beforeId 可空、category 可空、subjectRefs 可空 | items、snapshotMaxId、nextBeforeId 可空、checkedAt、historyGeneration |
| inspectReminderSubjects | 当前 context、带类型的原始 subjectRefs | 每个来源的事件 ID、状态、目标时间及查询状态 |
| beginReminderHistoryLogout | expectedHistoryGeneration、requestId、原始会话上下文 | 历史暂停结果、generation 及 purgeToken |
| finishReminderHistoryLogout | purgeToken | cleared、generation 或明确失败 |
| enableReminderHistorySession | 当前账号／epoch、expectedHistoryGeneration | 前台会话的历史绑定结果 |

页面每页固定 50 条，SQL 按 `id DESC`，续页使用 `id < beforeId`。首次读取返回首屏上界，后续页沿用该上界；切换过滤或主动刷新重新开始。历史代次变化返回 stale，页面清空旧游标。写入期间的插入与裁剪允许减少旧页行数，游标保证稳定顺序。

首屏 snapshotMaxId 取本账号当前历史代次的最大 id，后续查询同时限制 `id <= snapshotMaxId`。读请求验证正整数游标、支持的类别和带类型的事项引用；失效身份返回 stale，合法空集合返回空页。全部组来源超过单批查询大小时分批读完并合并，页面保留账号、代次和本机数据版本变化检查。

读取以当前账号／epoch 验证授权，历史行在当前历史代次内按账号查询，可包含该账号较早的业务 epoch。所有异步页面响应同时核对 Dart `accountEpoch`、原生 sessionEpoch 和 historyGeneration。

桥接失败使用 `history_unavailable`、`stale_session`、`stale_history_generation`、`invalid_history_argument`，Dart 严格解析。查询失败显示失败状态，保留的旧结果附原查询时间。未知 stage/reason 在显示层使用通用未知标签。

### 2.3 退出清理与晚到写入

历史控制使用独立原生 SharedPreferences 文件 `reminder_history_control`，保存 historyGeneration、recordingEnabled、ownerHash、ownerEpoch、purgePending、purgeToken、purgeRequestId、nextOperationSequence 和按账号的裁剪水位。该文件遵循现有只包含指定 FlutterSharedPreferences 的系统备份规则。这里的原生文件属于内部状态。

所有历史控制、上下文获取、追加和清理采用同一个原生锁，与历史表写入同步。开始退出时，先持久化本轮清理请求，再执行 begin 方法。begin 检查 expectedHistoryGeneration，原子推进 historyGeneration、关闭 recordingEnabled、清除 owner 绑定并保存 purgePending/token/requestId。相同请求返回既有结果。旧 generation 的请求返回 stale，迟到重试无法发起新的清理。

桥接不可用而暂缺 generation 时，本机只保存待清理意图。前台恢复先读取控制快照，把 expected generation 与请求 ID 持久化后再调用 begin；这一待清理意图处理完毕后才允许新会话启用历史。记录该本机标志的专用 key，并确认既有 repository.clear 不会将其提前清除。

finish 按 token 验证并删除所有账号的历史行及插件证据映射，成功后清除 purgePending；recordingEnabled 仍关闭，保留最后一次 requestId/token 作为幂等结果。崩溃或确认超时后使用同 token 重试。新 token 已生效时，旧 finish 返回 stale。

首装默认 generation=1、disabled、无 owner、无 pending。前台成功登录／会话恢复先读 getReminderHistoryControl，完成遗留 purge，再用该快照 generation 启用绑定并取得写上下文。退出后重登和进程重启采用同一顺序。后台引擎沿用已持久的 owner 绑定。桥接或清理暂时不可用时，课程与个人记录的正常操作继续完成，历史功能保持明确的待清理／不可用状态。控制状态的持久化失败返回 unavailable，由前台显示并重试。

旧异步写入的 historyGeneration 或 ownerEpoch 不匹配时返回 stale。开启新会话后，旧后台任务也无法取得旧账号的有效历史上下文。历史标志的保存及清理失败需要独立显示，不能由后续普通同步成功覆盖。

### 2.4 记录的观察出口

原生发布在实际 notify、active 检查、窗口延后和取消出口产出结构化结果；Receiver 也记录返回原因。插件内部的批次／单项操作生成不可变结果与观察对象，外层 `Future<void>` 继续执行现有失败合同。

新增插件观察回调带入本次 context，避免从后来的 Store 全局身份推断归属。正常安排、补偿恢复及撤销分别记录实际结果。业务操作及其补偿完成后，历史以独立事务尽力写入。日志故障通过独立 historyWarning 呈现，核心操作已完成的结果继续成立。

stage 固定为 scheduled、deferred、submitted、cancelled、blocked、scheduleFailed、cancelFailed、recoveryPending、unconfirmed。submitted 仅用于原生发布后 active 检查通过，标签写“提交后系统可见检查通过”。插件排期成功写 scheduled，目标时间过后缺少执行回执时显示结果未确认。

历史存储仅保存上述白名单字段。标题、通知正文、凭据、URL、原始异常文本通过已有当前数据或固定原因文案处理。测试通知使用单独测试结果反馈。

### 2.5 个人与摘要的当前排期证据

新增 `reminder_schedule_evidence`，主键为账号、历史代次、logicalKey。字段包含 sessionEpoch、operationSequence、subjectKind/subjectId、category、scheduledAt、notificationId、expectedPayload、state、confirmedAt。state 使用 confirmedScheduled、retainedOld、recoveryPending。该表保存当前证据，不受历史 30 天／500 条裁剪影响。

插件在 OS 安排成功后通过 recordReminderScheduleOutcome 写入目标时间、ID 和 payload；撤销成功后移除对应证据；替换失败保留有效旧证据，补偿与 journal 状态未确认时标记 recoveryPending。较旧 operationSequence 的晚到结果无法覆盖新证据。写入失败时当前原因返回 unconfirmed，核心安排结果继续按原合同反馈。

新增 `LocalNotificationService.readScheduleEvidence` 只读取得插件 pending 和 active 的 ID/payload/channel。Store 将其与桥接返回的证据映射相交核对。planned 要求当前账号／代次有效、映射处于已确认状态、目标为未来，并有匹配的 pending ID/payload。active 仅作当前可见事实，pending 缺失不能推出投递成功。

原 1.8.09 的个人／摘要排期没有这张映射，查询显示已有待投递记录但目标证据未确认。后续正常保存或显式恢复成功时建立映射。读取页面保持只读。历史清理同时清除该表；日常维护保留当前排期及未完成 journal 所需证据，移除已确认失效项。

inspectReminderSubjects 返回 nativeEvents 与 pluginEvidence 两组，逐项包含原始事项引用、类别、逻辑键、目标时间、通知 ID、当前状态和 evidenceAt。插件的实时 pending/active 查询状态由 Store 添加，桥接和插件查询分别报告错误。

## 3. 单项原因与功能入口

### 3.1 原因合同

`ReminderExplanation` 包含 checkedAt、subjectRefs、各类别的 status/reasonCodes/nextScheduledAt/evidenceAt/action，以及 queryWarnings。时间与原因使用同一查询快照。status 使用 planned、deferred、ineligible、unconfirmed、queryFailed。

在现有资格判定和计划生成位置增加结构化决定，旧布尔方法作为包装。公共同步方法的 `Future<void>` 合同继续由现有调用方使用。页面消费决定，纯规则和实际排期证据共同组成解释。

| 原因组 | 必须表达的情况 |
| --- | --- |
| 事项资格 | completed、hidden、unfollowed、outOfScope、statusUnknown、examNoticeOnly、examUnavailable |
| 时间与规则 | deadlineUnknown、deadlineReadFailed、noDeadline、anchorPassed、offsetWindowPassed、reminderDisabled |
| 新增提醒 | baselinePending、alreadyKnown、alreadySubmitted、newReminderDisabled |
| 调度与系统 | outsideWindow、cooldown、notificationPermissionOff、channelOff、permissionUnknown、channelUnknown、recoveryPending、scheduleUnconfirmed、queryFailed、inexactFallback |

可信无截止的课业可满足新增提醒资格，截止提醒显示 noDeadline。考试使用可信开考时间和现有考试生命周期／入口规则。个人使用提前 30 分钟，摘要沿用现有北京时间规则。精确权限不足且已成功回退时，把 inexactFallback 作为模式说明。

多个原因按事项资格、时间规则、开关、系统状态的顺序显示，查询失败单独标明缺少的证据。eligible 且算出未来计划只能证明规则满足；已有排期证据用于 planned。证据不完整则使用 unconfirmed。

### 3.2 多来源与隐藏项

从任一来源详情进入时，先用 courseworkGroupFor 查找整组，再取 group.sources 的全部原始 ID 查询。group.key 用于展示分组，原始 ID 用于 native 事件匹配，eventId 用于具体提醒。解析使用模型现有身份逻辑。

一组中有实际正式考试排期时，汇总展示该排期及其来源证据。仅通知来源的资格原因在来源详情中解释，完整原始来源均无资格时才形成整组资格结论。隐藏项从 localRecordGroups 查找，事项已移除显示通用名称和当前无法解析状态。

### 3.3 路由与页面

新增 `/reminder-history` 和 `/reminder-status/:kind/:id`，kind 只接受 assignment、manual、summary，ID 采用现有 URI 编码模式。页面由当前 Store 提供身份，路由参数只承担事项定位。

提醒体检增加“提醒记录与原因”入口，课业详情增加“提醒状态”，已保存个人日程编辑页在提醒开关附近增加“提醒状态”。个人编辑页查询已保存事项，另有未保存修改时显示该查询范围。

历史页按记录写入顺序倒序、每页 50 条，显示事实时间，提供全部及各提醒类别筛选。单项页显示查询时间、相关类别、已知下一次计划、原因和处理按钮。操作按钮只连接已有提醒设置、系统权限、同步详情或提醒恢复入口。
