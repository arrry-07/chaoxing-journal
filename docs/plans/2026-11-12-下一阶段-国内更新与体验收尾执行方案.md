## 4. A 批次：必须先闭环的提醒与协调修复

### A0. 两处会放大等待时间的租约缺陷（P1，源码确认）

不是泛泛的“可能卡顿”：下面两处控制流已核实；具体设备上的卡顿／ANR 尚未实测，不冒称已复现。

**A0-W：等待写锁时阻住了释放者。**

- 证据：`android/app/src/main/kotlin/com/example/studyassistant/BackgroundExecutionCoordinator.kt:71–99` 的 `acquireWrite`／`releaseWrite` 都带对象级 `@Synchronized`；内部等待另一个 `writeGate.monitor`。`wait()` 只释放内部 monitor，等待者仍持有对象锁，原持有者无法进入释放函数，直到等待超时。Bridge 的释放操作位于默认平台线程（`BackgroundReminderBridge.kt:180–190`），争用时还可能拖住主线程。
- 最小修改：去掉这两个函数冗余的对象级同步，仅由内部 monitor 保护 owner、depth；保留同 owner 重入、错误 owner 不释放、超时和 `releaseAllForOwner`。不取消互斥，不用自动过期锁或缩短超时掩盖问题。
- 新增 `android/app/src/test/kotlin/com/example/studyassistant/BackgroundExecutionCoordinatorTest.kt`：`waitingWriterDoesNotBlockOwnerRelease`、`sameOwnerIsReentrant`、`wrongOwnerCannotRelease`、等待超时、owner 销毁释放。使用 CountDownLatch（线程同步门闩）制造确定性争用，不依赖固定 sleep 等待“碰运气”；每个测试清理自己持有的租约。
- 验收：A 持有、B 等待，A 可及时释放、B 随即成功获得；重入两次必须对应释放两次；第三个请求可正常进入，不等 60 秒超时。

**A0-S：合并等待分支取得同步租约却提前返回。**

- 证据：`lib/src/services/assignment_store.dart:984–1032` 在 `lease.acquired` 后，“已有完整成功→重载返回”和“已有失败→返回”都位于 `try/finally` 之前。原生已把租约交给当前 requestId，提前返回就不会释放，下一轮可能等待至 120 秒上限。
- 最小修改：成功取得后立即进入统一 `try/finally`，覆盖合并成功、合并失败、重载异常、会话变化和正常同步；未取得租约不释放，release 使用原取得的 accountHash/requestId，不能取变化后的账号。
- 扩展 `assignment_store_background_reminder_test.dart` 的假网关，使其支持 `waited:true` 和释放计数；新增 `waitedSuccessReleasesSyncLease`、`waitedFailureReleasesSyncLease`、`reloadFailureStillReleasesLease`、未取得不释放。保留原来的同步合并节奏，不立即补一轮无界重试。
- 验收：每条取得后的路径恰好释放一次，紧接第二次刷新可完成；不误释放另一请求。

**A0-L：原生异步取得请求必须有取消／销毁生命周期。**

- 补查证据：`BackgroundReminderBridge.kt:149–170` 的后台任务在取得同步租约后再读数据库，未包异步异常清理；读失败可能既不应答也不释放。engine 销毁时只 `releaseAllForOwner` 一次，也挡不住仍在等待的任务随后重新取得。
- 区分“明确未取得”与“Dart 超时、原生取得结果不确定”：前者不释放他人的锁；后者必须按 requestId 做幂等取消／补偿，不能直接当未取得结束。为请求登记 engine owner／存活代次和取消状态，在等待唤醒及授予时于同一 monitor 下检查；销毁要使待取得请求失效并唤醒等待者，不只释放当前持有者。
- 取得后的数据库／组装错误在原生局部 `try/finally` 中释放本次取得，错误结果回主线程且只回复一次；迟到完成和取消竞态同样有终态。Dart 超时触发匹配 requestId 的取消；取消通道也失败时明确保留“租约状态未确认”的恢复／告警，不假报释放成功。必要的授予确认／迟到结果补偿应限定在请求协议，不给已开始运行的租约加自动过期。
- 新增 `acquiredLeaseReadFailureReleasesAndReplies`、`destroyedWaitingOwnerNeverReceivesLease`、`timedOutAcquisitionCannotLeakLateGrant`、`cancelDoesNotReleaseAnotherRequest`；覆盖同步和写租约。证明等待任务与控制／释放任务不在相互阻塞的同一执行器队列，主线程不阻塞等待 worker。

建议实施顺序：A0 的确定性失败测试与修复（包含异步请求生命周期及队列约束）→A1/A2→A3；这些都属于当前“提醒／协调 P1”范围，可分小提交留在现有 PR。新页面体验另作后续批次，不把完整托管部署混入此 PR。

### A1. 区分已投递旧插件通知与原生通知

**状态：确认缺陷，当前 PR 未完成。** [审查原文](https://github.com/arrry-07/chaoxing-journal/pull/16#discussion_r4548294655)。

涉及 Flutter 根下：

- `lib/src/services/local_notification_service.dart`：`removeLegacyAssignmentSchedules`、通知 ID／manifest／journal 的归属判断。
- `lib/src/services/assignment_store.dart`：`_legacyScheduleCleanupKey` 与 `_afterAssignmentsChanged`。
- 原生 `NativeReminderPolicy`、`ReminderDatabase`／桥接：必要时提供原生通知归属证据。
- `test/notification_ordering_test.dart`、`test/assignment_store_background_reminder_test.dart`。

问题：插件 v18 的 Android active 列表不提供 payload。早期已投递提醒可能既没有 pending request，也没有 v2 ID manifest；当前仅按 `a:` payload 的 active 过滤会漏清，然后永久记录迁移完成。反向改回“同渠道全删”又会误删原生通知，两者都不能作为修复。

已核实历史 `e1e75cb` 的 legacy 算法为 `FNV & 0x7fffffff` 后 `% 1700000000`；更早版本还用过进程相关 `Object.hash`。原生 `NativeReminderPolicy` 使用 `1_100_000_000 + (hashCode & 0x1fffffff)`，区间重叠，因此不能通过 ID 大小划界或只查数据库 ID 就完成归属判断。

**首选可执行设计（需原生测试证明，尚未实现）：**

1. 增加专门的 Android 旧作业迁移入口（拟新增 `LegacyAssignmentNotificationMigrator.kt`，名称不是现有接口）。从 `NotificationManager.activeNotifications` 读取完整 Notification，而不是依赖插件裁剪后的 map。
2. 插件 18.0.1 的已核实点击操作是 `packageManager.getLaunchIntentForPackage` + `SELECT_NOTIFICATION` + `requestCode=id`，使用 immutable Activity PendingIntent（不可变延迟操作）。以相同身份、`FLAG_NO_CREATE | FLAG_IMMUTABLE` 查询已有 token，与 active 通知的 `contentIntent` 比较；不触发、不创建、不更新 PendingIntent。原生通知使用独立 `ReminderClickActivity`、action 和 event URI，不能匹配。该判据须用锁定插件版本与真实已投递通知验证，不能仅靠 mock。
3. 只处理已证实属于旧作业的 `assignment_deadlines` 通知／`a:` pending／合法作业 manifest，排除已知测试通知；未知归属保留，报告未完成及重试入口。personal／summary 不在迁移范围。
4. 特别处理 ID 碰撞：插件 `cancel(id)` 也会删除同 ID 的 untagged active 通知，因此“pending 或清单属于旧插件”不代表可以裸 cancel。如果当前 active token 属于 native，必须只取消对应插件闹钟，并清理已证明归属的插件持久化调度记录，不能碰 active native；可在隔离的 v18 兼容适配器内实现固定版本的调度缓存／PendingIntent 清理，并为该 schema 加回归。不得以取消后重发 native 来伪装“保留”。无法可靠完成就返回未完成，不能强删。
5. 先完成 A0 的请求生命周期和队列约束。native 的 active 识别、最终检查和取消与投递使用共同串行边界；插件调度缓存另有**所有写入者**的约束：v18 插件 MethodChannel 方法、ScheduledNotificationReceiver 和 BootReceiver 默认都在同一进程 MainLooper 上运行，适配器的“读最新缓存→只移除目标→apply”也必须作为同一主线程短任务执行，不能在后台拿一份旧 JSON 改完整列表再覆盖。实施时核对 merged manifest 和 task queue 确认这个前提，不能拿只包 native 的 mutex 当全局保护。
   - 主线程临界区仅做必要的 token 复核、调度缓存内存读改写及最终短系统调用；耗时准备／可见性轮询在后台。native 发布的最终动作同样提交到这一串行边界，主线程不得等待持锁 worker，不能跨线程回调持锁互等。
   - apply 不是落盘成功：在不重写旧 JSON 的前提下建立可验证的持久化完成屏障（例如后台执行同一 SharedPreferences 的同步提交并检查结果，确认其涵盖之前的 apply）；在完成屏障成功前不写 v2 完成标记。失败保持 pending，不用读取缓存冒充落盘核验。
   - 保留所有非目标记录和其最新值；覆盖个人提醒恰好触发／续排、其他引擎插件方法、开机重建及缓存写入失败的交错测试。若未来插件写入线程／schema 改变，该固定版本适配器须重新验证，不静默沿用。
6. native 归属查询、active 枚举、取消或完成标记写入失败时，不标记永久完成；保留可重试状态，并在现有提醒警告／体检中显示原因。成功标记只能表示本轮完整迁移成功，不能只是“函数返回了”。
7. 将迁移完成标记升级为 v2（拟键 `legacy_assignment_schedule_cleanup_v2`），覆盖已被 v1 误判完成的安装。写入返回 false／异常后 reload 核实真实值；没有完整成功证据即继续 pending。不要把旧 v1 true 直接复制成 v2 true。
8. 不用 `cancelAll()`、不按共享 channel 全删，不取消正确 native 通知来取得测试通过。兼容适配器若不能在固定插件历史与 API26/35 证明身份匹配，先保留迁移 pending 并记录缺证，不切换成猜测删除。

必须补回归：

- 无 pending／manifest／payload 的已投递 legacy 与 native 共存：只清理 legacy。
- pending／清单 ID 与 native active 相同，以及迁移与个人提醒触发／续排并发：native 和非目标缓存保持最新，旧插件闹钟与缓存确实消失。
- 有／无通知 tag、未知 ID 和个人／摘要通知的保留。
- native 归属查询、active 枚举和逐条 cancel 分别失败：不落完成标记，下次能重试。
- 已有旧 v1 完成标记的升级仍执行修订迁移；新版本成功后不反复执行。
- 合法 native 保留；legacy manifest／journal 恢复仍正常；两次执行幂等。

### A3. 补齐关键控制操作的失败语义（P1，源码确认）

证据：`background_reminder_gateway.dart:139–165,333–337,383–399` 中 `clearActiveAccount`、`updateSettings`、`cancelAssignmentDeliveryKeepEvents` 等仍走吞错 helper；`assignment_store.dart:400–419,1340–1394,1802–1832,1947–1967` 在隐私清理、退出和控制更新中依赖这些结果。前轮严格化只覆盖部分方法，不能写成“原生桥已全部可靠”。

**影响：**原生取消失败仍可能清除待清理标记；原生设置更新失败后仍继续应用计划；退出在清理失败时丢掉旧 accountHash，后续难以针对旧账号重试。不能仅把异常放出来而让退出停在删除凭据之前。

实施：

1. 针对确有生产调用的关键写方法建立严格失败路径：上述三个方法及 `markPendingUpdate`、`ensureActiveAccount`、`switchAccount`、`reconcileDaytimeSchedule`；同步／写租约释放错误也需可见，不能假释放成功。`ensureActiveAccount`／`switchAccount` 当前还会吞错回 0（gateway:121–137），Store 登录的 `835–843` 会直接接受此值并设置 `nativeSwitched=true`，必须校验有效 epoch，确认后才提交 Dart 新身份。把原生切换失败纳入登录事务回滚／Cookie 清理，不能留在回滚 try 之外，也不能因失联假定旧 native 身份已经恢复。成功返回 null 的 void 方法另用严格 void helper，**不能直接套现有拒绝 null 的 `_invokeStrict<T>`**。有数据返回的方法检查应有字段和有效值。
2. 保留 `isAvailable` 的真正不支持平台降级；已确认 Android 桥存在后，缺插件、PlatformException、超时均为操作失败，不构造成功状态。
3. `_reconcileBackgroundControls` 返回明确的应用结果／失败状态；关键设置失败不能只写一个随后会被覆盖的 warning 然后继续 `applyPlan` 激活旧设置。复用现有 pending 状态，先确认控制应用再重排；本地已保存与原生已生效分开显示。
4. 隐私关闭的 native 清理或更新未确认时保留 durable pending（持久待处理状态），不要清 warning。不得声称旧原生提醒已停；应提示当前状态未确认、重试以及必要的系统通知关闭操作。
5. 退出采用尽力清理但必须完成本机身份／凭据清除；先持久保留需清理的旧账号 hash 与原因，再移除内存身份。失败后启动／重试可取回这个目标，在确认 native 清理成功后才移除待办；不保存密码、Cookie 或真实响应，不把这些内容写入日志。
6. A0-S 的 finally 与严格 release 一起审查：释放失败不能覆盖原始同步错误而完全丢失诊断，也不能误报成功释放。现有租约销毁释放作为兜底，不能替代正常控制流。

测试：扩展 `background_reminder_gateway_test.dart`、`notification_privacy_store_test.dart`、`aud001_notification_privacy_test.dart` 和后台 Store／登录测试；新增 `strictVoidAllowsSuccessfulNullReply`、`nativePrivacyFailureKeepsCleanupPending`、`nativeSettingsFailureDoesNotReportApplied`、`nativeSwitchFailureNeverCommitsNewIdentity`、`failedSwitchClearsNewCookiesWithoutClaimingRollback`、`daytimeScheduleFailureIsVisible`、`logoutRetriesNativeCleanupAfterIdentityRemoved`。覆盖异常、缺插件、超时、成功 void/null、标记持久化失败及重启重试。只把方法名改成 strict 而不测调用方失败恢复，不算完成。

### D3. 上线、容量与失败分支

- 顺序：唯一 APK→匿名完整回下载→manual→适用 major/minor 时才更新 stable→匿名重新读取。1.7.5 补丁不得写入 stable。
- **首次初始化国内 stable 的特例要显式处理：**它是引入已公开的 `1.7.4+56` 基线，而不是发布一个新补丁。先用真实的上一已发布 `1.7.3+55` 和核验过的1.7.4 APK通过 `-Channel manual` 生成1.7.4 JSON；确认国内 stable 入口此前不存在且 GitHub 当前稳定基线仍是1.7.4后，将这份完全相同、已验证的基线 JSON 用作初始 stable。两类清单 JSON 契约相同，channel 只控制生成策略。部署工具须用显式“首次初始化”操作并拒绝覆盖已有 stable，保留所依据的正式 Release、签名及摘要证据。不得对1.7.4调用 `-Channel stable -PreviousVersionName 1.7.3`（脚本会正确拒绝同minor补丁），也不得伪造旧上一版本来绕过门禁。之后1.7.5只更新manual，stable仍指向1.7.4；若稳定基线已变，重新核对而不是照搬此例。
- 保留最新约 8 份不同 APK 作为初始建议；80% 容量提示。清理先输出引用／待删除清单，确认后才删；不删 stable/manual/迁移说明引用项，不动 GitHub 历史。
- Gitee 要求用户登录、禁止分发、限额不足或清单不稳定：标记候选失败，保留 GitHub；不改后缀、拆包、多账号绕限制。

- 开发机无代理测试只证明该网络；移动数据／宽带分别验收，不能写“三网无障碍”。

定向测试至少包括：`update_manifest_test.dart`、`silent_update_policy_test.dart`、`github_update_channel_test.dart`、`apk_download_transport_test.dart`、`update_parallel_download_test.dart`；脚本测试另跑，不把 Dart 清单解析测试冒充发布脚本执行测试。

### 8.1 必须补齐的原生门禁
